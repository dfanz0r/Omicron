# Implementation Plan 0001.5: Pre-Provider Cleanup

Status: Complete  
Target: clean up Plan 1 transitional code before starting Plan 2 provider API abstraction.

## Purpose

Plan 1 established the core architectural groundwork: host composition, sessions, events, extensions, tool registry, workspace/execution seams, provider state, provider registry, and model catalog.

Before starting Plan 2, we should remove avoidable transitional complexity and code smells so provider-stateful API work does not build on unstable seams.

This plan is intentionally small. It should not implement OpenAI Responses, canonical conversation transforms, provider compatibility descriptors, or stateful/stateless fallback logic. Those remain Plan 2.

## Goals

1. Remove or isolate legacy MVP code paths that can diverge from `AgentSession`.
2. Move provider-state event emission out of the raw store.
3. Clarify execution request/session-scoping semantics.
4. Improve event-writing ergonomics enough to avoid scatter as Plan 2 adds provider events.
5. Split broad architecture tests into focused test files.
6. Update docs so Plan 2 starts from an accurate baseline.

## Non-Goals

- Do not implement real OpenAI Responses API.
- Do not introduce a full canonical conversation format.
- Do not build provider compatibility descriptors yet.
- Do not build persistence.
- Do not build sandboxing.
- Do not rewrite model discovery into provider-contributed discovery unless it is trivial while touching catalog code.

## Work Items

### 1. Remove or fully retire legacy `Agent`

Current issue:

`Omicron.Core/Agent/Agent.cs` remains a second agent loop. The CLI now uses `AgentSession`, but tests and older code still compile against `Agent`. Keeping two agent loops risks divergence during Plan 2 provider work.

Preferred outcome:

- Delete `Agent` and legacy `AgentEvent`/`AgentEventType` if no current production code depends on them.
- Update or remove tests that cover the old agent path.
- If removal is too disruptive, make `Agent` a thin compatibility wrapper over `AgentSession` and mark it `[Obsolete]`.

Recommendation:

Try deletion first. If only tests break, update tests to `AgentSession`. Avoid keeping compatibility code unless there is a real consumer.

Acceptance criteria:

- No active code path uses the old `Agent` loop.
- Tests cover `AgentSession` as the only supported session/agent runtime.
- `dotnet test` passes.

### 2. Introduce `ProviderStateManager`

Current issue:

`InMemoryProviderConversationStateStore` is both storage and event producer. That coupling is acceptable as an MVP shim but awkward for Plan 2, where provider-state updates need richer context.

Target design:

```csharp
public interface IProviderStateManager
{
    ProviderTurnState? Get(ProviderStateKey key);
    ProviderTurnState Set(ProviderTurnState state, string? reason = null);
    void Clear(ProviderStateKey key, string? reason = null);
    void ClearSession(SessionId sessionId, string? reason = null);
    IReadOnlyList<ProviderStateKey> GetSessionKeys(SessionId sessionId);
}
```

Implementation:

- `InMemoryProviderConversationStateStore` becomes storage-only.
- New `ProviderStateManager` wraps `IProviderConversationStateStore` and `IEventSink`.
- Manager emits `ProviderStateUpdatedEvent` / `ProviderStateClearedEvent`.
- `OmicronHost.ProviderState` should expose the manager or both manager and store with clear naming.
- `AgentSession` should receive/use the manager, not the raw store, for reset clearing.

Plan 2 can later enrich manager methods/events with storage policy, previous-vs-new IDs, fallback reason, etc.

Acceptance criteria:

- Raw store has no `IEventSink` dependency.
- Provider-state event tests exercise `ProviderStateManager`.
- `AgentSession.Reset()` clears provider state through manager and emits clear events.
- No provider-state event has sequence `0` after sink stamping.

### 3. Clarify execution request session semantics

Current issue:

`ExecutionRequest.SessionId` is optional and events are suppressed when absent. This is safe but ambiguous.

Preferred outcome:

Make session-scoped execution explicit:

```csharp
public sealed record ExecutionRequest(
    SessionId SessionId,
    string Command,
    string? ShellId,
    string? WorkingDirectory,
    int TimeoutSeconds = 120,
    ToolCallId? ToolCallId = null);
```

If non-session execution is needed later, add a separate method or request type:

```csharp
ExecuteUnscopedAsync(...)
```

For now, shell tool executions are session-scoped, so required `SessionId` is simpler and safer.

Acceptance criteria:

- `ExecutionRequest.SessionId` is required.
- `LocalExecutionBroker` always emits execution events for brokered execution.
- Tests are updated.
- There are no synthetic/random execution session IDs.

### 4. Add a minimal session event writer/factory

Current issue:

Event construction is scattered. The sink stamps sequence numbers, but producers still manually stamp `EventId.New()` and `DateTimeOffset.UtcNow` everywhere.

Target design:

Introduce a small helper, not a heavy framework:

```csharp
public interface ISessionEventWriter
{
    SessionId SessionId { get; }
    OmicronEvent Emit(OmicronEvent evt);
}
```

or an internal `SessionEventWriter` used by `AgentSession`.

Do not overbuild. The main goal is to give Plan 2 a clear place to emit provider request/state/fallback events.

Possible implementation:

```csharp
public sealed class SessionEventWriter
{
    private readonly IEventSink _sink;
    public SessionId SessionId { get; }

    public T Emit<T>(T evt) where T : OmicronEvent
        => (T)_sink.Emit(evt);
}
```

Acceptance criteria:

- `AgentSession` uses the writer/helper instead of directly calling `_eventSink.Emit` everywhere.
- ProviderStateManager can use the same event sink/writer pattern.
- Sequence stamping remains owned by `IEventSink`.

### 5. Split architecture tests by subsystem

Current issue:

`ArchitectureTests.cs` is a broad catch-all and is becoming hard to review.

Target files:

```text
EventSinkTests.cs
ProviderStateTests.cs
AgentSessionTests.cs
ExecutionBrokerTests.cs
ModelCatalogTests.cs
ExtensionRegistryTests.cs
WorkspaceTests.cs
CommandRegistryTests.cs
ToolRegistryTests.cs
```

Keep test behavior the same while moving code. Avoid mixing large behavioral changes into the split if possible.

Acceptance criteria:

- `ArchitectureTests.cs` is deleted or reduced to only true cross-cutting architecture tests.
- Tests remain readable and focused.
- `dotnet test` passes.

### 6. Update documentation and plan status

Update:

- `docs/rfcs/IMPLEMENTATION-BASELINE.md`
- `docs/implementation-plans/0001-core-architecture-groundwork.md`
- optionally `README.md`

Document:

- `AgentSession` is the supported runtime.
- Legacy `Agent` removed or wrapper-only.
- Provider state manager exists and is the Plan 2 handoff point.
- Event sequence is currently global per event sink.
- Model catalog is still centralized; provider-extensible discovery deferred to Plan 2.
- Credential env-var metadata still deferred to Plan 2.
- Shell escaping/sandbox hardening deferred.

Acceptance criteria:

- Docs match code reality.
- Plan 2 can begin without rediscovering Plan 1 assumptions.

## Suggested Implementation Order

1. Split tests first or last, but not in the same commit as behavior changes if possible.
2. Remove/retire legacy `Agent` and update tests.
3. Add `ProviderStateManager` and make store storage-only.
4. Make `ExecutionRequest.SessionId` required.
5. Add minimal `SessionEventWriter` helper.
6. Update docs.
7. Run full build/test.

## Definition of Done

Plan 1.5 is complete when:

- old `Agent` is removed, or reduced to a clearly obsolete wrapper with no independent loop;
- provider state mutations go through `ProviderStateManager`;
- raw provider state store does not emit events;
- execution requests are explicitly session-scoped;
- event writing has a small reusable helper/writer;
- tests are split by subsystem;
- docs and baseline are updated;
- all tests pass with no warnings.

## Plan 2 Handoff

After this cleanup, Plan 2 should use:

- `AgentSession` as the only active runtime path;
- `IModelCatalog` for model/API classification;
- `IProviderRegistry` for provider lookup/registration;
- `ProviderStateManager` for `previous_response_id`, conversation IDs, session affinity, and state-clearing behavior;
- `IEventSink` / event writer for provider request, response, fallback, and state events;
- `ToolRegistry` and `ToolInvocationContext` for tool/function-call round trips.
