# Implementation Plan 0003.7: API Shape, Async Boundaries, and Model Metadata

Status: **Draft / Ready for implementation**  
Predecessor: Plan 3.6 hardening complete  
Successor: Plan 4 transaction-backed edit harness

---

## Purpose

Plan 3.7 addresses architectural critiques discovered after Plan 3.6 review. These are not long-term backlog items; they should shape the immediate core API before Plan 4 builds more functionality on top.

Primary goals:

1. Replace growing host/session parameter lists with domain request/config objects.
2. Add async-first host APIs and audit `Task`/`ValueTask` usage deliberately.
3. Introduce model metadata discovery foundations for static catalogs, `models.dev`, and provider `/models` endpoints.

Non-goals:

- Do not fully implement every provider-specific model metadata endpoint.
- Do not build UI for metadata refresh yet.
- Do not redesign provider runtime APIs around metadata.
- Do not make blanket `ValueTask` conversions without reason.

## Phase 1: Session Creation API Shape

### Problem

`OmicronHost.CreateSession(...)` currently takes several separate optional parameters and internally creates `SessionConfig`:

```csharp
public AgentSession CreateSession(
    Model model,
    string? systemPrompt = null,
    string? apiKey = null,
    int? maxTokens = null,
    double? temperature = null,
    int maxIterations = 100)
```

This fights the architecture introduced in Plan 3.6, where `SessionConfig` became the canonical immutable session configuration object.

### Changes

1. Add async-first primary API:

```csharp
public ValueTask<AgentSession> CreateSessionAsync(
    SessionConfig config,
    CancellationToken ct = default);
```

2. Add sync convenience wrapper:

```csharp
public AgentSession CreateSession(SessionConfig config);
```

3. Keep the existing parameter-list overload only temporarily as a convenience wrapper, or mark it as legacy/internal depending on call-site impact:

```csharp
public AgentSession CreateSession(
    Model model,
    string? systemPrompt = null,
    string? apiKey = null,
    int? maxTokens = null,
    double? temperature = null,
    int maxIterations = 100)
    => CreateSession(SessionConfig.Create(...));
```

4. Update CLI and tests to construct `SessionConfig` explicitly before calling host APIs.

5. Audit `ResumeSessionAsync` and `ForkSessionAsync` signatures. If they also need multiple session/provider settings, introduce small request objects instead of adding more parameters:

```csharp
public sealed record SessionResumeRequest(
    SessionId SessionId,
    Model Model,
    string? ApiKey = null);

public sealed record SessionForkRequest(
    SessionId SourceSessionId,
    Model Model,
    string? SystemPrompt = null,
    string? ApiKey = null);
```

Only add these request records if the implementation starts accumulating more parameters; otherwise leave resume/fork alone for this plan.

### Tests

- Existing session creation tests updated to use `SessionConfig`.
- Add test proving `CreateSessionAsync(SessionConfig)` creates a session record with config values.
- Add test proving sync `CreateSession(SessionConfig)` delegates correctly.

### Completion Criteria

- `SessionConfig` is the primary session creation input.
- Parameter-list overload no longer contains core construction logic.
- CLI/test call sites prefer `SessionConfig`.
- Build/test remain clean.

## Phase 2: Async API and `ValueTask` Audit

### Problem

Some APIs are async-first, while others synchronously block on async store calls. Example:

```csharp
SessionStore.CreateSessionAsync(request).GetAwaiter().GetResult();
```

Plan 3.7 should set conventions before remote stores/TUI/background workers make sync-over-async more risky.

### Guidelines

Use `ValueTask` when:

- the operation often completes synchronously;
- the API is an abstraction implemented by both in-memory and async/durable backends;
- the result is awaited once;
- avoiding allocation on hot paths is useful.

Use `Task` when:

- work is inherently asynchronous;
- the returned operation may be stored, awaited multiple times, or composed broadly;
- API ergonomics are more important than avoiding a possible allocation.

Avoid:

- converting APIs to `ValueTask` blindly;
- exposing sync-only APIs over async storage;
- hiding sync-over-async inside core host APIs.

### Changes

1. Add async-first host methods where synchronous host APIs currently block:

```csharp
public ValueTask<AgentSession> CreateSessionAsync(SessionConfig config, CancellationToken ct = default);
```

2. Keep sync wrappers only for CLI/simple test convenience:

```csharp
public AgentSession CreateSession(SessionConfig config)
    => CreateSessionAsync(config).AsTask().GetAwaiter().GetResult();
```

3. Audit these areas and document decisions in the plan/review:

- `OmicronHost`
- `ISessionStore`
- `IEventSink`
- `WorkspaceTransaction`
- `WorkspaceTransactionManager`
- `SlashCommandDispatcher`

4. Do **not** convert CLI slash dispatch to async in this plan unless necessary. Existing FH-0011 still tracks full async slash command dispatch.

### Tests

- Existing tests should pass unchanged or be updated for async host API.
- Add one async test for `CreateSessionAsync` persistence behavior.

### Completion Criteria

- Core host session creation is async-first.
- Sync wrapper is explicit and isolated.
- `ValueTask` usage is intentional and documented.
- No new sync-over-async added outside wrappers.

## Phase 3: Model Metadata Architecture

### Problem

Model metadata is currently mostly static/catalog-defined. In practice, metadata may need to come from:

- bundled/static catalog defaults;
- `models.dev`;
- provider-specific endpoints such as `/models`;
- user config overrides.

Omicron needs a foundation for model metadata refresh and merge without coupling runtime provider calls to Chat Completions assumptions.

### Design Principles

- Keep runtime provider instances separate from metadata.
- Metadata should describe capabilities, not dictate provider transport shape.
- Merge metadata deterministically.
- Treat external metadata as cacheable and fallible.
- Do not require network metadata for basic CLI startup.

### New Core Types

Add a model metadata surface under `Omicron.Core/Models/`:

```csharp
public sealed record ModelMetadata(
    string ModelId,
    string ProviderName,
    string? DisplayName = null,
    int? ContextWindow = null,
    int? MaxOutputTokens = null,
    bool? SupportsTools = null,
    bool? SupportsReasoning = null,
    bool? SupportsVision = null,
    bool? SupportsStructuredOutput = null,
    decimal? InputPricePerMillionTokens = null,
    decimal? OutputPricePerMillionTokens = null,
    DateTimeOffset? LastUpdatedAt = null,
    string? Source = null);
```

Add source abstraction:

```csharp
public interface IModelMetadataSource
{
    string Name { get; }

    ValueTask<IReadOnlyList<ModelMetadata>> LoadAsync(
        CancellationToken ct = default);
}
```

Add merge service:

```csharp
public interface IModelMetadataMerger
{
    IReadOnlyList<ModelMetadata> Merge(
        params IReadOnlyList<ModelMetadata>[] sources);
}
```

Recommended merge order:

1. bundled/static baseline;
2. `models.dev`;
3. provider `/models` endpoint;
4. user config overrides.

Later sources override earlier sources only for fields they explicitly provide.

### Initial Sources

Implement minimal MVP sources:

1. `StaticModelMetadataSource`
   - converts existing bundled model catalog data into `ModelMetadata`.

2. `ModelsDevMetadataSource` skeleton
   - interface and placeholder implementation only if network policy/API details are not ready;
   - should fail closed and return empty list on errors.

3. Provider endpoint source abstraction:

```csharp
public interface IProviderModelMetadataSource : IModelMetadataSource
{
    string ProviderName { get; }
}
```

Do not fully implement every provider endpoint in this plan. Add one simple provider source only if already straightforward.

### Integration

- Extend `ModelCatalogService` so metadata can be layered onto existing `Model` entries.
- Do not remove existing static catalog behavior.
- CLI `/models` may continue showing current fields, but should be able to use enriched metadata if present.

### Tests

Add tests for:

- metadata merge precedence;
- null fields do not overwrite known fields;
- static metadata source maps known catalog fields;
- failed external source does not break catalog loading.

### Completion Criteria

- `ModelMetadata` and source abstractions exist.
- Static metadata can be produced from current catalog.
- Merge behavior is deterministic and tested.
- No provider runtime code depends on metadata refresh being available.

## Exit Criteria

- Build: 0 warnings, 0 errors.
- Tests: all existing tests pass, with new tests for session creation and metadata merge behavior.
- `OmicronHost.CreateSession(SessionConfig)` is the preferred sync API.
- `OmicronHost.CreateSessionAsync(SessionConfig, ct)` is the preferred core API.
- No new large optional-parameter session creation APIs are introduced.
- `ValueTask`/`Task` usage decisions are documented.
- Model metadata architecture exists without making startup/network availability fragile.
