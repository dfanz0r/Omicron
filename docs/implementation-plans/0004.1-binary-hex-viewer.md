## Purpose

When an LLM agent reads a file via `read_path`, the tool must decide how to return the content based on:

1. **What kind of file is this?** — text, image, PDF, audio, office document, or unknown binary.
2. **What can the current model consume?** — vision support, PDF support, audio support, or text-only.
3. **What format did the model request?** — the model can override automatic detection via a `format` parameter.

Currently, `read_path` handles text and rejects everything else as "binary." Plan 4.1 builds a model-aware adaptive pipeline that extracts, encodes, or hex-dumps binary content based on the current model's capabilities.

**Editing binary files is out of scope.** This plan is read-only.

### Design Constraints

- **No commercial libraries.** GroupDocs, Aspose, Syncfusion, GemBox are excluded.
- **No AI/cloud dependencies.** Microsoft.Extensions.DataIngestion, Azure Document Intelligence, cloud OCR are excluded. Everything must run locally for local models.
- **No unmaintained wrappers.** TikaOnDotNet is excluded.
- **Open-source per-format libraries only.** PdfPig, OpenXml, ClosedXML, AngleSharp, MimeKit, SharpCompress, etc.
- **Dynamic registration.** Format handlers are registered at host construction, not hardcoded. Different model configurations may register different handler sets.
- **Cross-model portability.** When moving a session between models, modalities used in the session must be validated against the target model. Fail early if unsupported.

## Current State (Post-Plan-4)

- `TextEncodingDetector.IsText()` — content-based text/binary detection (BOM, null-byte, UTF-8 decode, printable ratio).

Missing:

- No format-specific handling for images, PDF, audio, etc.
- No model-capability awareness in the read tool.
- No hex dump mode for binary inspection.
- No `format` override parameter on `read_path`.
- No local format extractors (PDF text, DOCX text, etc.).

## Architecture

### Decision Flow

When `read_path` is called on a file:

```
1. Read file bytes.

2. Check the `format` parameter:

   format == "hex"    → HexDumpProcessor directly (bypass classification).
                        offset/limit interpreted as byte offsets.

   format == "base64" → Base64Processor directly (bypass classification).
                        Returns raw base64 string. MIME type determined
                        from magic bytes + extension.

   format == "text"   → TextProcessor directly (bypass classification).
                        Attempts UTF-8 decode. If IsText() returns false,
                        includes a [WARNING: binary file] prefix.

   format == "auto"   →
     3. Classify by extension + magic bytes (Phase 1):
        ├─ Image           → ImageProcessor
        ├─ Pdf             → PdfProcessor
        ├─ Audio           → AudioProcessor
        ├─ Video           → VideoProcessor
        ├─ OpenXmlDocument  → OpenXmlProcessor
        ├─ LegacyDocument  → LegacyOfficeProcessor
        ├─ Csv             → CsvProcessor
        ├─ Email           → EmailProcessor
        ├─ Ebook           → EbookProcessor
        ├─ Archive         → ArchiveProcessor
        ├─ Notebook        → NotebookProcessor
        ├─ Svg             → TextProcessor (XML text with size cap)
        ├─ Text            →
        │    4. Run TextEncodingDetector.IsText() as safety check:
        │       ├─ IsText() = true  → existing text reading path
        │       └─ IsText() = false → reclassify as UnknownBinary
        └─ UnknownBinary   → HexDumpProcessor

5. Each processor receives model metadata in ContentProcessorContext
   and adapts its output accordingly (base64 for capable models,
   extracted text or hex dump for text-only models).

6. The processor emits a ModalityUsedEvent if the output is
   ImageBase64, PdfBase64, AudioBase64, or VideoBase64.
```

**Key design decision:** Classification runs *before* the text/binary check, not after. Many structured formats (CSV, EML, IPYNB, SVG) are technically valid UTF-8 text and would never reach a specialized processor if `IsText()` ran first. The classifier uses extension + magic bytes as the primary signal; `IsText()` is a safety check only on files classified as `Text`.

The `format` parameter lets the model override:

| `format` value | Behavior |
|---------------|----------|
| `"auto"` (default) | Automatic: classify file → resolve processor → model-aware output |
| `"text"` | Force UTF-8 decode. If `TextEncodingDetector.IsText()` returns false, include a `[WARNING: binary file]` prefix but still attempt decode. |
| `"hex"` | Force hex dump regardless of file type. `offset` and `limit` reinterpreted as byte offsets. |
| `"base64"` | Force raw base64. Output format: `[FILE] path (MIME, N bytes)\n{base64_data}`. No line wrapping on the base64 payload. |

### Model Capability Matrix (from report)

| Capability | `modalities.input` | Behavior |
|-----------|-------------------|----------|
| Vision | contains `"image"` | Images → base64 inline with MIME type |
| PDF native | contains `"pdf"` | PDF → base64 inline with `application/pdf` |
| Audio | contains `"audio"` | Audio → base64 inline with MIME type |
| Video | contains `"video"` | Video → base64 inline with MIME type |
| Text-only | only `"text"` | Everything → extracted text, metadata, or hex dump |

### Key Types

```csharp
/// <summary>
/// Context passed to every IContentProcessor.ProcessAsync call.
/// Contains everything the processor needs to decide how to handle the file.
/// </summary>
public sealed record ContentProcessorContext(
    string AbsolutePath,
    string RelativePath,          // workspace-relative, for error messages
    ReadOnlyMemory<byte> Bytes,   // full file bytes (already read)
    long FileSize,                // from stat
    SessionId SessionId,          // for ModalityUsedEvent emission
    ModelMetadata? ModelMetadata, // null if model capabilities unknown
    string Format,                // "auto", "text", "hex", or "base64"
    int? Offset,                  // byte offset (hex mode) or line offset (text mode)
    int? Limit,                   // byte limit (hex mode) or line limit (text mode)
    IEventSink? EventSink,        // for emitting ModalityUsedEvent
    CancellationToken CancellationToken);

/// <summary>
/// Result returned by IContentProcessor.ProcessAsync.
/// Carries the actual output modality used (which may differ from
/// the processor's declared capabilities).
/// </summary>
public sealed record ContentProcessorResult(
    string Text,                          // formatted output for the model
    OutputModality ActualModality,        // what was actually emitted
    string? MimeType = null,             // e.g., "image/png"
    string? Warning = null,              // e.g., "PDF text extracted locally"
    bool IsTruncated = false,            // true if output was cut short
    long? NextOffset = null);            // for continuation (hex or text)
```

## Phase 1: File Type Classification

### New file: `Omicron.Core/IO/FileTypeClassifier.cs`

Detects file type by combining MIME sniffing (magic bytes) and extension:

```csharp
public enum DetectedFileType
{
    Text,           // UTF-8 or BOM-family text (including source code, config, Markdown)
    Image,          // PNG, JPG, GIF, WebP, BMP, ICO
    Pdf,            // application/pdf
    Audio,          // MP3, WAV, FLAC, OGG, AAC
    Video,          // MP4, AVI, MOV, WebM
    OpenXmlDocument,// DOCX, XLSX, PPTX (ZIP container with Open XML content)
    LegacyDocument, // .doc, .xls, .ppt (binary Office formats)
    Csv,            // CSV, TSV (text but parseable as structured data)
    Email,          // .eml, .msg
    Ebook,          // EPUB
    Notebook,       // IPYNB (Jupyter)
    Archive,        // ZIP, TAR, 7z, GZip, BZip2
    Svg,            // text/xml but treated as text with size cap
    UnknownBinary   // everything else
}

public static class FileTypeClassifier
{
    public static DetectedFileType Classify(string path, ReadOnlySpan<byte> header);
}
```

Uses:
- Magic byte signatures from first 16 bytes (PNG `89 50 4E 47`, PDF `25 50 44 46`, ZIP `50 4B 03 04`, etc.).
- **ZIP subtype detection:** When magic bytes indicate ZIP, the classifier opens the archive (via `System.IO.Compression.ZipArchive` from the already-read bytes) and checks for signature entries:
  - `[Content_Types].xml` → `OpenXmlDocument` (DOCX/XLSX/PPTX)
  - `META-INF/container.xml` → `Ebook` (EPUB)
  - Neither → `Archive` (generic ZIP/TAR/7z)
- Extension fallback for formats without reliable magic bytes (`.mp3`, `.wav`, `.csv`, `.ipynb`, `.svg`, `.eml`).
- The method signature accepts full file bytes, not just a header, to support ZIP inspection:
  `public static DetectedFileType Classify(string path, ReadOnlySpan<byte> bytes);`

## Phase 2: Dynamic Content Processor Registry

### Design

Format handlers are **not hardcoded**. They are registered at host construction through a `ContentProcessorRegistry`. Different model configurations can register different handler sets. Extensions can contribute format handlers just as they contribute tools and commands.

### New file: `Omicron.Core/IO/ContentProcessorRegistry.cs`

```csharp
/// <summary>
/// A format handler that can read and process a specific file type.
/// Returns either extracted text, base64-encoded inline data, hex dump, or metadata.
/// </summary>
public interface IContentProcessor
{
    /// <summary>Unique identifier for this processor.</summary>
    string Id { get; }

    /// <summary>Which file types this processor handles.</summary>
    IReadOnlySet<DetectedFileType> SupportedTypes { get; }

    /// <summary>
    /// All output modalities this processor CAN produce (flags).
    /// The ACTUAL modality per invocation is on ContentProcessorResult.ActualModality.
    /// Not used for session porting — that uses the runtime ActualModality.
    /// </summary>
    OutputModality OutputModality { get; }

    /// <summary>
    /// Process a file and return formatted content for the model.
    /// Receives model capabilities so it can adapt (e.g., skip base64 for text-only models).
    /// </summary>
    ValueTask<ContentProcessorResult> ProcessAsync(
        ContentProcessorContext context,
        CancellationToken ct = default);
}

/// <summary>
/// Registry that dispatches file reads to the appropriate IContentProcessor.
/// Processors are tried in registration order; first one that supports the
/// detected file type wins.
/// </summary>
public sealed class ContentProcessorRegistry
{
    public void Register(IContentProcessor processor);
    public IContentProcessor? Resolve(DetectedFileType fileType);
    public IReadOnlyList<IContentProcessor> RegisteredProcessors { get; }
}
```

### Output Modality Enum

```csharp
/// <summary>
/// What kind of data a content processor can emit.
/// A processor's OutputModality property declares all modalities it
/// MIGHT produce. The ContentProcessorResult.ActualModality records
/// what was ACTUALLY emitted for a specific invocation.
///
/// Used for cross-model session porting validation:
/// if a session emitted ImageBase64, the target model must support "image".
/// </summary>
[Flags]
public enum OutputModality
{
    None        = 0,
    Text        = 1 << 0,  // Plain text or Markdown — works with any model
    ImageBase64 = 1 << 1,  // base64-encoded image inline data — requires vision
    PdfBase64   = 1 << 2,  // base64-encoded PDF inline data — requires pdf modality
    AudioBase64 = 1 << 3,  // base64-encoded audio inline data — requires audio modality
    VideoBase64 = 1 << 4,  // base64-encoded video inline data — requires video modality
    HexDump     = 1 << 5,  // Structured hex dump — always works (it's just text)
    Metadata    = 1 << 6,  // File metadata only (dimensions, codec, size, etc.)
}
```

**Property vs actual:** `IContentProcessor.OutputModality` is a `[Flags]` enum declaring what the processor *can* produce. `ContentProcessorResult.ActualModality` records what was *actually* emitted. Only the actual modality is recorded in `ModalityUsedEvent`.

### Built-in Processors (using open-source libraries only)

| Processor | Library dependency | File type | Declared OutputModality |
|-----------|-------------------|-----------|------------------------|
| `TextProcessor` | none (built-in) | Text | `Text` |
| `ImageProcessor` | `SixLabors.ImageSharp` (BSD) | Image | `ImageBase64 \| HexDump \| Metadata` |
| `PdfProcessor` | `PdfPig` (Apache 2.0) | Pdf | `PdfBase64 \| Text` |
| `AudioProcessor` | none (built-in) | Audio | `AudioBase64 \| Metadata` |
| `VideoProcessor` | none (built-in) | Video | `VideoBase64 \| Metadata` |
| `OpenXmlProcessor` | `DocumentFormat.OpenXml` (MIT) | OpenXmlDocument | `Text` |
| `LegacyOfficeProcessor` | `NPOI` (Apache 2.0) | LegacyDocument | `Text` |
| `CsvProcessor` | `CsvHelper` (MS-PL/Apache 2.0) | Csv | `Text` |
| `EmailProcessor` | `MimeKit` (MIT) | Email | `Text` |
| `ArchiveProcessor` | `SharpCompress` (MIT) | Archive | `Text` |
| `NotebookProcessor` | none (built-in, System.Text.Json) | Notebook | `Text` |
| `EbookProcessor` | `VersOne.Epub` (MIT) | Ebook | `Text` |
| `SvgProcessor` | none (built-in) | Svg | `Text` |
| `HexDumpProcessor` | none (built-in) | UnknownBinary | `HexDump` |
| `Base64Processor` | none (built-in) | *(format override only)* | `ImageBase64 \| PdfBase64 \| AudioBase64 \| VideoBase64` |

**Notes:**
- `AudioProcessor` and `VideoProcessor` have no external library dependency. They parse container headers (ID3, RIFF, MP4, MKV) for basic metadata (duration, codec, sample rate, dimensions, bitrate) and return `Metadata` for text-only models, `AudioBase64`/`VideoBase64` for capable models. No transcoding.
- `SvgProcessor` reads SVG as XML text with a 1 MB size cap. Identical behavior to reading a text file but with an explicit size limit.
- `Base64Processor` is only used when `format: "base64"`. It determines MIME type from magic bytes + extension. It is never resolved from the registry by file type.
- `HexDumpProcessor` is the universal fallback for `UnknownBinary`. Other processors may also delegate to hex dump internally when the model lacks the required modality (e.g., `ImageProcessor` for text-only models), returning `ActualModality = HexDump`.

**Archive processor output:** Returns a table of contents (file tree with sizes, compressed/original size, modification dates). Does **not** recursively extract. The model must use `execute_command` with `unzip` / `tar` / `7z` if it needs file contents from the archive.

### Hex Dump Format

Standard hexdump:

```
Offset    00 01 02 03 04 05 06 07  08 09 0A 0B 0C 0D 0E 0F  Decoded
--------  -------------------------------------------------  ----------------
00000000  50 4B 03 04 14 00 00 00  08 00 00 00 00 00 00 00  |PK..............|
00000010  00 00 00 00 00 00 00 00  00 00 00 00 00 00 00 00  |................|
```

Rules:
- Offset column: 8-char zero-padded hex, absolute byte position in the file.
- Hex bytes: 16 per row, grouped 8+8 with extra space.
- ASCII column: printable (0x20–0x7E) shown as-is; everything else → `.`.
- Null bytes → `00` in hex, `.` in ASCII.
- Default: first 256 bytes (16 rows). Max: 512 bytes (32 rows) per call.
- All-zero rows rendered (no elision).

### Hex Dump Offset / Chunking

The existing `offset` and `limit` parameters on `read_path` are **reinterpreted as byte offsets** when `format: "hex"`. Both accept integer or `0x`-prefixed hex string values:

```json
{
  "path": "large.dat",
  "format": "hex",
  "offset": "0x200",
  "limit": "0x100"
}
```

This returns bytes 512–767 (inclusive) as a hex dump. The offset column starts at `00000200` (512 in hex), not `00000000`. Decimal integers (`offset: 512`) are also accepted — the `0x` prefix determines the radix.

If the file extends beyond the requested window, a continuation hint is appended:

```text
... (showing bytes 0x200–0x2FF of 0x1000 total. Use offset=0x300 to continue.)
```

### Edge Case: Offset / Range Normalization

The model may request arbitrary offsets that don't align to row boundaries, or ranges that overrun the file. The hex dumper normalizes these to produce clean, well-formed rows with no wasted context:

**Offset rounding:** The requested `offset` is always rounded **down** to the nearest 16-byte row boundary (`offset & ~0xF`). If the model requests `offset: 20`, the dump starts at row `00000010` (byte 16). The requested target byte will appear in the correct position within that row.

**End-of-file truncation:** If `offset + limit` exceeds the file size, the range is clamped to the file end. The final row may be a **partial row** — fewer than 16 hex bytes, blank columns for missing bytes, and a blank ASCII column for missing positions. Example:

```
Offset    00 01 02 03 04 05 06 07  08 09 0A 0B 0C 0D 0E 0F  Decoded
--------  -------------------------------------------------  ----------------
00000180  AB CD EF                                              |...             |
```

The partial row is always shown — no zero-padding, no whitespace filler where bytes don't exist in the file.

**Offset beyond file:** If `offset >= fileSize`, return an empty result with the file size:

```text
[FILE] data.bin  (binary, 512 bytes)
Requested offset 1024 is past end of file (512 bytes).
```

**Rounding down to zero:** If `offset < 16`, the dump starts at row `00000000`.

**`limit=0`:** Returns an empty hex dump (header row only, no data rows). Not an error — the model may want to confirm a file exists and is binary without consuming context.

**`0x` hex parsing:** Both `offset` and `limit` accept `0x`-prefixed strings or plain decimal integers. Invalid hex strings (e.g., `"0xGG"`, `"hello"`) return a clear error:

```text
Error: offset "0xGG" is not a valid hex value. Use decimal (512) or 0x-prefixed hex (0x200).
```

Negative offsets are rejected: `"Error: offset must be non-negative."`

These rules ensure the output is always structurally valid and never wastes context on invisible padding or misleading zero-filled rows.

// On ToolInvocationContext:

### Step 3d: Processor adaptation

The `ContentProcessorContext` passed to each processor includes the current model's metadata, so processors can adapt:

- `ImageProcessor` returns `ImageBase64` for vision models, `HexDump` for text-only models.
- `PdfProcessor` returns `PdfBase64` for PDF-capable models, extracted `Text` for others.

## Phase 5: Wire Into `read_path` Tool

Modify `BuiltinWorkspaceToolsExtension.read_path` handler:

1. Read file bytes.
2. Check `format` parameter:
   - `"hex"` → use `HexDumpProcessor` directly, skip to step 5.
   - `"base64"` → use `Base64Processor` directly, skip to step 5.
   - `"text"` → use `TextProcessor` directly, skip to step 5.
   - `"auto"` → continue to step 3.
3. Call `FileTypeClassifier.Classify(path, bytes)`.
4. Resolve `IContentProcessor` from `ContentProcessorRegistry` for the detected type.
   If the type is `Text` → run `TextEncodingDetector.IsText()` as safety check.
   If `IsText()` returns false → reclassify as `UnknownBinary` → `HexDumpProcessor`.
   If no processor registered for the type → `HexDumpProcessor`.
5. Build `ContentProcessorContext` with model metadata, `format`, file bytes, path, session ID.
6. Call `processor.ProcessAsync(context, ct)`.
7. Emit `ModalityUsedEvent` if `result.ActualModality` requires it.
8. Return formatted result.

### Track Modalities Used in Session

When a processor returns `ImageBase64`, `PdfBase64`, `AudioBase64`, or `VideoBase64`, the pipeline emits a `ModalityUsedEvent` to the session event log. This enables cross-model porting validation (Phase 6).

```csharp
/// <summary>
/// Emitted when a content processor produces output that requires
/// a specific model modality. Persisted in the session event log
/// for cross-model porting validation.
/// </summary>
public sealed record ModalityUsedEvent(
    EventEnvelope Envelope,
    string Modality,            // "image", "pdf", "audio", or "video"
    string RelativePath,        // workspace-relative path of the file
    OutputModality OutputKind)   // ImageBase64, PdfBase64, AudioBase64, or VideoBase64
    : OmicronEvent(Envelope, "modality_used");
```

Registration:

```csharp
// In OmicronEventRegistry:
registry.Register<ModalityUsedEvent>("modality_used");
```

Emission (in the `read_path` handler or processor pipeline):

```csharp
if (result.ActualModality is OutputModality.ImageBase64 or OutputModality.PdfBase64
    or OutputModality.AudioBase64 or OutputModality.VideoBase64)
{
    var modality = result.ActualModality switch
    {
        OutputModality.ImageBase64 => "image",
        OutputModality.PdfBase64 => "pdf",
        OutputModality.AudioBase64 => "audio",
        OutputModality.VideoBase64 => "video",
        _ => throw new InvalidOperationException()
    };

    await ctx.EventSink!.EmitAsync(new ModalityUsedEvent(
        EventEnvelope.ForSession(ctx.SessionId),
        modality, ctx.RelativePath, result.ActualModality));
}
```

Note: `ContentProcessorContext` needs `SessionId` for this. Add it to the context record. `HexDump`, `Text`, and `Metadata` modalities are **not** recorded — they work with any model.

## Phase 6: Cross-Model Session Porting Modality Validation

### Problem

When a user moves a session from a vision-capable model to a text-only model, any previous tool results that contain base64 image data become meaningless. The target model cannot interpret them. The session should **fail early** — before the model is changed — with a clear diagnostic.

### Approach

Add a validation step to `OmicronHost.ForkSessionAsync` and `OmicronHost.ResumeSessionAsync` that checks modality compatibility **before** creating the new session.

```csharp
/// <summary>
/// Validate that the target model supports all modalities used in the source session.
/// Returns a diagnostic listing unsupported modalities with affected files, or empty if compatible.
/// </summary>
public static async ValueTask<IReadOnlyList<ModalityValidationError>> ValidateModalityCompatibilityAsync(
    ISessionStore store,
    SessionId sourceSessionId,
    ModelMetadata targetModelMetadata,
    CancellationToken ct = default)
{
    // Load ModalityUsedEvents from the session event log.
    var events = await store.GetEventsAsync(sourceSessionId, ct);
    var modalityEvents = events.OfType<ModalityUsedEvent>().ToList();

    if (modalityEvents.Count == 0)
        return Array.Empty<ModalityValidationError>();

    // Group by modality string.
    var byModality = modalityEvents.GroupBy(e => e.Modality);
    var errors = new List<ModalityValidationError>();

    foreach (var group in byModality)
    {
        if (!targetModelMetadata.SupportsModality(group.Key))
        {
            errors.Add(new ModalityValidationError(
                group.Key,
                group.Select(e => e.RelativePath).Distinct().ToList()));
        }
    }

    return errors;
}

public sealed record ModalityValidationError(
    string Modality,
    IReadOnlyList<string> AffectedFiles);
```

### UX

When modalities are incompatible, the fork/resume operation returns an error:

```text
Cannot fork session abc123 to model deepseek-v3.
The source session used modalities not supported by the target model:
  - image (2 files: screenshot.png, diagram.jpg)
  - pdf (1 file: report.pdf)

Choose a model that supports these modalities, or continue with the current model.
```

The session remains on the original model — no partial state change.

### Persistence

`ModalityUsedEvent` is emitted by the content processor pipeline and stored in the session event log. This makes modality usage queryable from the event stream without scanning tool results.

## Phase 7: Tests

**Classifier:**
- `FileTypeClassifier` correctly identifies PNG, PDF, ZIP/OpenXml, MP3, EML, EPUB from magic bytes.
- `FileTypeClassifier` distinguishes DOCX/XLSX/PPTX from generic ZIP by checking for `[Content_Types].xml`.
- `FileTypeClassifier` distinguishes EPUB from generic ZIP by checking for `META-INF/container.xml`.
- `FileTypeClassifier` falls back to extension for formats without reliable magic bytes (`.mp3`, `.wav`, `.csv`, `.ipynb`, `.svg`).
- `FileTypeClassifier` classifies `.csv` and `.ipynb` before the text/binary check (they are valid UTF-8).
- `FileTypeClassifier` returns `Text` for unknown-but-valid-UTF-8 files and `UnknownBinary` for unknown binary files.

**Hex dump:**
- `HexDumpProcessor` produces correct offset, hex bytes, ASCII columns.
- `HexDumpProcessor` handles empty file, partial final row, mid-file truncation, continuation hint.
- `HexDumpProcessor` rounds offset down to nearest 16-byte row boundary.
- `HexDumpProcessor` clamps range to file end (partial row, no zero-padding).
- `HexDumpProcessor` returns clean error for offset past end of file.
- `HexDumpProcessor` handles `limit=0` (empty output, no error).
- `HexDumpProcessor` rejects invalid `0x` hex strings and negative offsets with clear errors.
- `HexDumpProcessor` accepts both `"0x200"` and `512` for offset/limit.

**Processor registry:**
- `ContentProcessorRegistry` resolves correct processor for each `DetectedFileType`.
- `ContentProcessorRegistry` returns `HexDumpProcessor` as fallback for unregistered types.
- Extensions can register custom `IContentProcessor` via default interface method.

**Model-aware behavior:**
- `ImageProcessor` returns hex dump (`ActualModality = HexDump`) for text-only model.
- `ImageProcessor` returns base64 (`ActualModality = ImageBase64`) for vision model.
- `PdfProcessor` returns extracted text (`ActualModality = Text`) for text-only model.
- `PdfProcessor` returns base64 (`ActualModality = PdfBase64`) for PDF-capable model.

**`read_path` integration:**
- `format: "hex"` on a PNG returns hex dump regardless of model capabilities.
- `format: "base64"` returns raw base64 with MIME header regardless of model capabilities.
- `format: "auto"` selects correctly per model capabilities for each file type.
- `read_path` on a text file is unaffected (regression).
- `read_path` with `ModelMetadata = null` (unknown model) uses safe defaults (text extract / hex dump, never base64).

**Modality events and porting:**
- `ModalityUsedEvent` is emitted when `ActualModality` is `ImageBase64`, `PdfBase64`, `AudioBase64`, or `VideoBase64`.
- `ModalityUsedEvent` is persisted in session event log and deserializes correctly.
- `ValidateModalityCompatibility` passes when target supports all used modalities.
- `ValidateModalityCompatibility` fails with diagnostic listing each unsupported modality and affected files.
- Fork to text-only model from vision session returns error; original session unchanged.

**Graceful degradation:**
- All processors handle empty files and corrupt/malformed content without throwing.
- Processors with missing NuGet dependencies are silently skipped at registration (debug log).
- `read_path` on a file type with no registered processor falls back to `HexDumpProcessor`.

## Non-Goals

- No binary file editing.
- No streaming binary reads.
- No real-time audio/video transcoding.
- No OCR for images.
- No PDF page-to-image rendering (future plan).
- No user-attachment pipeline (separate concern per report).

## Exit Criteria

- Build: 0 warnings, 0 errors.
- Tests: all existing + new binary format tests pass.
- `read_path` returns appropriate content for images, PDF, audio, Office docs, and unknown binary.
- `read_path` respects model capabilities (no images sent to text-only models).
- `format` parameter overrides automatic detection.
- Hex dump available as universal fallback.
- Text file reads unaffected (no regression).
