# Implementation Plan 0003.1: Omicron Native Diff Engine

Status: Implemented — ready for Plan 3 Phase 4 transaction integration.  
Date: 2026-05-08  
Related plan: `0003-core-persistence-workspace-foundations.md` Phase 4  
Reference material: `READ_ONLY/Diff` Myers implementation, used as algorithm/reference only — do not copy as-is.

## Purpose

Plan 3 Phase 4 needs workspace transaction diffs that are better than naive line-by-line comparison. We want a native Omicron diff engine that provides high-quality text diffs for staged workspace changes while fitting Omicron's architecture and modern C# style.

The external `READ_ONLY/Diff` implementation is useful as an algorithm reference, but it is older C# and allocation-heavy. Omicron should implement its own diff engine with Omicron-owned API/types, tests, and rendering behavior.

## Goals

Build a full line-based text diff engine suitable for:

- workspace transaction preview;
- future edit harness diagnostics;
- future UI/web diff components;
- future LLM-facing patch summaries;
- deterministic tests and replay/debug output.

The engine should:

- produce minimal or near-minimal edit scripts using Myers-style O(ND) diff;
- support repeated lines well;
- expose structured edits/hunks separately from text rendering;
- render unified-ish text diffs for LLM/tool output;
- avoid old .NET collection patterns;
- be internal/core-owned and replaceable.

## Non-Goals

Do not implement in this phase:

- binary diffing;
- semantic/AST-aware code diffing;
- word-level or character-level intraline highlighting;
- patch application;
- three-way merge;
- rename detection by similarity;
- streaming/incremental diffing;
- native/Rust diff engine;
- UI-specific diff widgets.

## Design Principles

1. **Structured first, rendered second**

   The algorithm returns structured edits/hunks. Rendering to unified text is a separate step.

2. **Workspace-neutral**

   The diff engine should not depend on `IWorkspaceFileSystem`, transactions, events, or renderers.

3. **Deterministic**

   Same input lines must produce the same edits and rendered output across machines/cultures.

4. **Modern C# baseline**

   Use generics and simple allocations first. Avoid legacy `Hashtable`, `ArrayList`, mutable public fields, and per-line regex work.

5. **Optimization later, but don't paint into a corner**

   Start with arrays/lists. Keep implementation shaped so `ArrayPool<T>` can be added later for large diffs if profiling warrants it.

## Public/Internal API

Keep the engine internal initially unless other assemblies need it.

```csharp
namespace Omicron.Core.Diff;

internal static class TextDiffEngine
{
    public static TextDiffResult DiffLines(
        IReadOnlyList<string> oldLines,
        IReadOnlyList<string> newLines,
        TextDiffOptions? options = null);
}
```

```csharp
internal sealed record TextDiffOptions
{
    public static TextDiffOptions Default { get; } = new();

    public bool TrimWhitespace { get; init; }
    public bool IgnoreWhitespaceRuns { get; init; }
    public bool IgnoreCase { get; init; }

    /// <summary>
    /// Optional. If true, shift ambiguous changes downward when repeated equal lines
    /// make the edit script more readable without changing edit distance.
    /// </summary>
    public bool OptimizeForReadability { get; init; } = true;
}
```

```csharp
internal sealed record TextDiffResult(
    IReadOnlyList<TextDiffEdit> Edits,
    int OldLineCount,
    int NewLineCount)
{
    public bool HasChanges => Edits.Count > 0;
}
```

```csharp
internal readonly record struct TextDiffEdit(
    int OldStart,
    int OldCount,
    int NewStart,
    int NewCount)
{
    public bool IsInsert => OldCount == 0 && NewCount > 0;
    public bool IsDelete => OldCount > 0 && NewCount == 0;
    public bool IsReplace => OldCount > 0 && NewCount > 0;
}
```

Index conventions:

- `OldStart` and `NewStart` are **0-based** line indexes.
- `OldCount` and `NewCount` are counts.
- Rendering converts to 1-based unified diff line numbers.

## Algorithm Spec

Implement line-based Myers diff.

### Step 1: Normalize comparable tokens

Input is `IReadOnlyList<string>`. Do not split text inside the algorithm.

Map lines to integer codes using a shared dictionary across old and new lines:

```csharp
var codes = new Dictionary<string, int>(StringComparer.Ordinal);
```

Normalization only applies to the comparison key, not the rendered line text:

- `TrimWhitespace`: `line.Trim()`
- `IgnoreWhitespaceRuns`: collapse whitespace runs to single space
- `IgnoreCase`: use `StringComparer.OrdinalIgnoreCase` or normalize with invariant casing

For Phase 4, default all ignore options to false.

### Step 2: Fast trim common prefix/suffix

Before running Myers, trim equal prefix and suffix:

```text
old[prefix] == new[prefix]
old[oldEnd - 1] == new[newEnd - 1]
```

This reduces work and improves behavior on mostly-equal files.

### Step 3: Myers shortest edit script

Implement Myers O(ND) shortest edit script over integer arrays.

Recommended implementation options:

#### Required approach: multiple strategies with fallback

Support multiple exact diff strategies behind one `TextDiffEngine` facade. The lower-memory divide-and-conquer Myers variant should be available as the high-safety fallback path, not necessarily the only implementation.

Rationale:

- trace-based Myers is easier to implement/debug and can be fast for small/medium inputs;
- divide-and-conquer Myers uses less memory and is safer for high-edit-distance large inputs;
- workspace transaction previews may encounter generated files, lockfiles, rewritten files, vendored files, or model-generated whole-file rewrites;
- a core diff algorithm should produce exact diffs without semantic line-count caps or fake partial edits;
- a strategy/fallback design lets us optimize common cases while preserving correctness and memory safety.

Proposed internal strategy shape:

```csharp
internal interface ITextDiffStrategy
{
    string Name { get; }
    bool CanRun(TextDiffInputStats stats, TextDiffOptions options);
    TextDiffResult Diff(IReadOnlyList<int> oldCodes, IReadOnlyList<int> newCodes, TextDiffOptions options);
}
```

Initial strategies:

```text
TraceMyersDiffStrategy
  - preferred for small/medium inputs and low estimated edit distance
  - can keep trace snapshots for simple reconstruction

DivideAndConquerMyersDiffStrategy
  - fallback/default-safe path for large or high-risk inputs
  - shortest-middle-snake recursion
  - O(N + M) working memory plus recursion/output

CoarseOmittedDiffStrategy / ResourceLimitDiffStrategy (optional future)
  - explicit metadata-only omitted diff if all exact strategies decline due to budget/cancellation
  - must not fabricate plausible partial edits
```

Fallback selection:

```text
TextDiffEngine.DiffLines(...):
  normalize lines to comparable integer codes
  trim common prefix/suffix
  compute cheap input stats:
    - old/new line count
    - middle-section line count
    - maybe unique-token overlap estimate
  try trace strategy if within safe thresholds
  otherwise use divide-and-conquer strategy
  if selected strategy fails due to resource/cancellation, fall back to divide-and-conquer
  if all exact strategies fail under explicit caller budget, return explicit ResourceLimitExceeded/Omitted status
```

Divide-and-conquer high-level:

```text
DiffRange(oldLo, oldHi, newLo, newHi):
  trim equal prefix/suffix
  if old range empty: emit insert
  if new range empty: emit delete
  else:
    find middle snake with forward/reverse Myers search
    DiffRange(left side before middle snake)
    skip middle snake equal region
    DiffRange(right side after middle snake)
```

Implementation should use reusable forward/reverse vectors sized to the current full input or to the active range. Do not snapshot full V arrays per edit distance in the fallback strategy.

`READ_ONLY/Diff` may be used as algorithm reference for the shortest-middle-snake structure, but do not copy it as-is. Implement Omicron-owned types, names, tests, and style.

### Step 4: Convert edit path to compact edits

The final edit result should merge adjacent additions/deletions into `TextDiffEdit` records.

Examples:

- insert 2 lines at old index 5:

```csharp
new TextDiffEdit(OldStart: 5, OldCount: 0, NewStart: 5, NewCount: 2)
```

- delete 3 old lines at old index 10:

```csharp
new TextDiffEdit(OldStart: 10, OldCount: 3, NewStart: 10, NewCount: 0)
```

- replace one old line with two new lines:

```csharp
new TextDiffEdit(OldStart: 4, OldCount: 1, NewStart: 4, NewCount: 2)
```

### Step 5: Readability optimization

Implement an optional readability optimization similar in spirit to the external library, but with Omicron-owned code.

Purpose:

- repeated blank lines/braces can create multiple valid minimal edit scripts;
- shift ambiguous edits downward when doing so makes the hunk more natural;
- do not change semantic edit distance.

Initial rule:

Given a modified run in old or new side, if the first changed comparable token equals the first unchanged comparable token after the run, move the change marker down one line. Repeat until stable.

This can be implemented either:

- on boolean modified arrays before building edits; or
- on `TextDiffEdit` records after initial script generation.

Prefer applying to internal modified arrays if using an LCS/modified-array approach; otherwise implement post-processing carefully with tests.

The option must be disableable through `TextDiffOptions.OptimizeForReadability` for deterministic algorithm tests.

## Allocation/Performance Guidance

MVP target:

- no legacy non-generic collections;
- avoid regex in default path;
- avoid splitting strings in the engine;
- arrays for code buffers and vectors;
- `List<T>` for edits/hunks;
- use `StringComparer.Ordinal` for deterministic keys/sorts.

Use `Span<T>` / `ReadOnlySpan<T>` where it materially reduces allocations or improves hot-path performance without compromising correctness. The diff engine is allowed to be more performance-conscious than the rest of the MVP because it may run over large files during transaction previews.

Preferred optimization posture:

- use spans for normalization/scanning helpers where practical;
- avoid allocating intermediate normalized strings unless the line actually needs normalization;
- consider `ArrayPool<int>` for code arrays and Myers vectors from the first implementation if the code remains clear;
- consider `ArrayPool<bool>` if using modified arrays;
- avoid `Regex` in whitespace normalization;
- add benchmarks or stress tests before making complex pooling/span code too clever;
- avoid semantic line-count cutoffs inside the core algorithm; if resource limits are needed, model them as caller policy or explicit resource-budget failure, not as a fake partial diff.

## Workspace Transaction Integration

Transaction diff generation should use this engine.

Suggested `WorkspaceFileDiff` shape:

```csharp
public sealed record WorkspaceFileDiff(
    WorkspacePath Path,
    WorkspaceChangeKind Kind,
    string? OldPath,
    string? TextDiff,
    bool IsBinary,
    bool IsDirectory);
```

For text files:

1. decode old/new bytes as UTF-8;
2. normalize line endings to LF for diffing;
3. split into lines consistently with `WorkspaceReadService`;
4. call `TextDiffEngine.DiffLines(oldLines, newLines)`;
5. render with `UnifiedDiffRenderer.Render(...)`;
6. store rendered text in `WorkspaceFileDiff.TextDiff`.

Resource policy should live at the workspace transaction/rendering layer, not as a silent semantic change in the core algorithm. Strategy selection may use safe thresholds to choose trace vs divide-and-conquer, but should not use line-count caps to fabricate partial edits. If a future resource budget is added and all exact strategies decline, exceeding it should produce an explicit failure/omitted-diff status, not a plausible partial edit script.

For binary files:

- do not decode;
- set `IsBinary = true`;
- `TextDiff = null` or a short metadata-only message.

## Line Splitting Contract

Use one helper for diff line splitting, not ad hoc `Split` calls everywhere.

```csharp
internal static class TextLineSplitter
{
    public static IReadOnlyList<string> SplitLines(string text);
}
```

Initial behavior should match current workspace read behavior:

```csharp
text.Replace("\r\n", "\n").Replace("\r", "\n").Split('\n')
```

Trailing newline behavior:

- a final empty line is preserved because `Split('\n')` does that by default;
- this matches current workspace read behavior and should be tested.

## Test Requirements

### Engine tests

Port behavior tests inspired by `READ_ONLY/Diff/TestCases.cs`, without copying code directly:

- all changes;
- all same;
- insertion at beginning/end;
- deletion at beginning/end;
- replacement in middle;
- snake case: old `a,b,c,d,e,f`, new `b,c,d,e,f,x`;
- repeated-line ambiguity;
- historical-style repro with mixed insert/delete around repeated lines;
- empty old -> added file;
- non-empty old -> empty new;
- both empty.

Assert on `TextDiffEdit` records.

### Renderer tests

- modified file includes `---`, `+++`, hunk header, removed and added lines;
- added file uses `/dev/null` old path;
- deleted file uses `/dev/null` new path;
- context line count respected;
- large rendered diff truncates at configured limits;
- no-change diff renders empty string or a stable no-change marker — choose one and test it.

Recommendation: render empty string for no changes.

### Workspace transaction tests

When integrated into Phase 4:

- modified text file diff includes real minimal hunk;
- added text file diff;
- deleted text file diff;
- binary file change does not render binary content;
- repeated-line file produces readable/stable hunk.

## Acceptance Criteria

The native diff engine is complete when:

- Omicron has its own diff engine implementation under Omicron namespace;
- external `READ_ONLY/Diff` code is not copied verbatim;
- structured `TextDiffEdit` results are produced from line arrays;
- unified text rendering is separate from the algorithm;
- deterministic tests cover common insert/delete/replace/repeated-line cases;
- renderer tests cover unified output;
- workspace transaction diffs use this engine;
- build/test pass with zero warnings.
