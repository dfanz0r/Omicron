## High-Priority Findings

### 1. Event delivery now has two paths: yielded session stream vs event sink side-channel

Files:

- `Omicron.Core/Sessions/AgentSession.cs`
- `Omicron.Core/Execution/IExecutionBroker.cs`
- `Omicron.Core/Sessions/ProviderStateManager.cs`

`AgentSession.PromptAsync()` yields events it emits directly through `SessionEventWriter`. But `LocalExecutionBroker` and `ProviderStateManager` emit directly to the shared `IEventSink`. Those events are recorded in `host.EventLog`, but they are not yielded from `AgentSession.PromptAsync()`.

That means a frontend consuming only:

```csharp
await foreach (var evt in session.PromptAsync(...))
```

will see session/tool/model events, but not execution events or provider-state events emitted by lower services during tool invocation.

This is not a test failure, but it is an architectural decision that should be explicit before Plan 2 adds provider request/state/fallback events.

Recommendation:

Choose and document one of these models:

1. **Event sink is authoritative, stream is a convenience subset.** Frontends needing complete event streams subscribe/read from the sink.
2. **`AgentSession` async stream is authoritative.** All nested service events must be routed back into the yielded stream.
3. **Hybrid with dispatcher/subscriptions.** `PromptAsync()` yields high-level UI events; event sink stores full audit events.

Given current code, option 1 or 3 is likely easiest. But Plan 2 must know which one is true.

Acceptance suggestion:

- Add a short design note to Plan 1.5/baseline.
- Consider renaming/positioning `PromptAsync()` as a live UI stream, while `IEventSink` is durable/audit stream.

## Medium-Priority Findings

### 2. `SessionEventWriter` documentation overstates what it does

File: `Omicron.Core/Events/SessionEventWriter.cs`

The XML doc says:

```text
Stamps EventId.New() and DateTimeOffset.UtcNow automatically
```

But implementation only delegates to the sink:

```csharp
public T Emit<T>(T evt) where T : OmicronEvent
{
    return (T)_sink.Emit(evt);
}
```

`AgentSession` still manually constructs `EventId.New()` and `DateTimeOffset.UtcNow` for every event.

Recommendation:

Either:

- update the comment to match reality; or
- add helper methods/factory methods that actually stamp IDs/timestamps.

For Plan 2, a real writer/factory would be useful because provider events will otherwise repeat a lot of boilerplate.

Minimal fix now: correct the XML doc.

---

### 3. `ProviderStateManager.Set()` emits event using possibly unnormalized key

File: `Omicron.Core/Sessions/ProviderStateManager.cs`

`InMemoryProviderConversationStateStore.Set()` normalizes the key before storage. But `ProviderStateManager.Set()` emits the event using the original `state.Key`:

```csharp
_store.Set(state);
_eventSink?.Emit(new ProviderStateUpdatedEvent(..., state.Key, ...));
return state;
```

If a caller constructs a key directly with `"OpenAI"`, the stored key is normalized to `"openai"`, but the event key and returned state still contain `"OpenAI"`.

Recommendation:

Normalize in the manager before storing/emitting:

```csharp
var normalizedKey = state.Key.Normalize();
var normalizedState = state with { Key = normalizedKey };
_store.Set(normalizedState);
_eventSink?.Emit(... normalizedKey ...);
return normalizedState;
```

This keeps storage and event identity consistent.

---

### 4. `ProviderStateManager.Clear()` emits clear events even when no state was removed

File: `Omicron.Core/Sessions/ProviderStateManager.cs`

Current behavior:

```csharp
_store.Clear(key);
_eventSink?.Emit(new ProviderStateClearedEvent(...));
```

This emits a clear event even if the key never existed. The previous raw-store behavior only emitted when removal succeeded.

Recommendation:

Either:

- make `IProviderConversationStateStore.Clear(...)` return `bool`; or
- check `_store.Get(key)` before clearing; or
- explicitly document clear events as idempotent commands rather than state-change events.

For audit/replay clarity, I recommend emitting only when state existed.

---

### 5. `ProviderStateManager` accepts `reason` but drops it

File: `Omicron.Core/Sessions/ProviderStateManager.cs`

Methods accept:

```csharp
string? reason = null
```

but events do not include it and the value is unused.

Recommendation:

For Plan 1.5, either remove `reason` until Plan 2 adds richer provider-state events, or add `Reason` to `ProviderStateUpdatedEvent` / `ProviderStateClearedEvent`.

Dropping it silently is a small smell and can mislead Plan 2 implementers.

---

### 6. `IEventSink.EmitBatch(...)` still returns `void`

File: `Omicron.Core/Events/IEventSink.cs`

`Emit(...)` returns the stamped event, but `EmitBatch(...)` returns nothing. If batch emission is used later, callers cannot observe stamped sequences.

Recommendation:

Change to:

```csharp
IReadOnlyList<OmicronEvent> EmitBatch(IReadOnlyList<OmicronEvent> events);
```

or remove `EmitBatch` until needed.

Not urgent, but better to fix before more event infrastructure builds on it.

## Lower-Priority Findings

### 7. `ProviderStateKey.Create(...)` should guard null/empty provider names

File: `Omicron.Core/Sessions/ProviderState.cs`

Currently:

```csharp
providerName.ToLowerInvariant()
```

will throw if `providerName` is null. Nullable annotations may prevent most misuse, but public APIs should either validate cleanly or document assumptions.

Recommendation:

Add argument validation for `providerName` and `modelId`.

---

### 8. Execution broker event emission remains optional via nullable sink

File: `Omicron.Core/Execution/IExecutionBroker.cs`

`LocalExecutionBroker` accepts `IEventSink?`. In host usage it gets a sink, so this is fine. But because `ExecutionRequest.SessionId` is now required, a broker with no sink silently records no events.

Recommendation:

This is acceptable for tests or standalone use, but consider making the default host path the only production construction path. No action required now.

---

### 9. Shell escaping remains deferred

File: `Omicron.Core/Execution/IExecutionBroker.cs`

Generic shell escaping remains a known future hardening item. This is acceptable for Plan 1.5 as long as execution/sandbox work revisits it.

No immediate action required before Plan 2 provider work.

4. Make provider-state clear events conditional on actual state removal.
5. Remove or wire `reason` parameter.

After that, Plan 2 can start on much cleaner ground.
