## Executive Summary

The original status report is **mostly correct on direction and completion level**, but it **overstates two areas**:

1. **Plan 0017 outbound provider serialization is further along than reported**: runtime request sending already uses `WriteRequestBody(Utf8JsonWriter, ...)` through `ShapeBasedProvider`. The remaining work is removing the old `BuildRequestBody(): JsonObject` compatibility surface, not adding writer overrides from scratch.
2. **Plan 0020 adoption is overstated**: `Utf8CompositeFormat` and `PreparedUtf8CompositeFormat` are implemented and tested, but there is **no current production usage found** in `Omicron.Core` or `Omicron.CLI`. The pipeline exists; broad migration has not happened yet.

Aside from those corrections, the broad conclusion stands:

> The UTF-8 foundation is now real and substantial. `Utf8String`, message/event migration, raw-byte provider ingest, UTF-8 event persistence, canonical conversation migration, and the composite formatting engine are all in place. Remaining work is mostly fan-out cleanup, compatibility-surface removal, and lower-priority hotspot polish.

### Confirmed partial / still open

### Solidified verdict

**Plan 0016 is substantially advanced but not complete.**  
Phases 1, 2, and much of 4 are in good shape. Phases 5, 6, and 8 remain partial.

## Plan 0017 — UTF-8 Message Pipeline Migration

### Confirmed completed

- `Message` no longer uses the old dual `Text` / `Utf8Text` bridge shape.
- `Message.TextData` / `ReasoningData` now use `Utf8String`.
- explicit boundaries now exist:
  - `TextUtf8`
  - `ReasoningUtf8`
  - `GetTextString()`
  - `GetReasoningString()`
- `AgentSession` stores user/assistant/tool-result text as `Utf8String`.
- `SessionProjection` reconstructs messages as `Utf8String`-backed.
- `Conversation` content items are UTF-8-native:
  - `TextContentItem(Utf8String)`
  - `ToolResultContentItem(..., Utf8String Text, ...)`
  - `ReasoningContentItem(Utf8String? Summary, ...)`
- provider streaming ingest is byte-oriented in the shared runtime path:
  - `ShapeBasedProvider` uses raw `ReadAsStreamAsync()` reads
  - SSE lines are scanned from bytes
  - `ParseSseChunk(ReadOnlyMemory<byte>, ...)` is the active interface
- event persistence uses UTF-8 byte serialization helpers via `OmicronEventJson`.

### Important correction to the original report

The report said provider request-body migration was only partial because shapes still need to override `WriteRequestBody(...)` directly.

That is **no longer accurate**.

Confirmed from source:

- `ShapeBasedProvider` sends requests by calling `shape.WriteRequestBody(jsonWriter, ...)`
- `OpenAiChatShape`, `OpenAiResponsesShape`, and `AnthropicShape` all implement `WriteRequestBody(...)`

What remains is different:

- `IApiShape` still exposes legacy `BuildRequestBody(...): JsonObject`
- the default interface implementation of `WriteRequestBody(...)` still delegates through `BuildRequestBody(...)`
- each concrete shape still keeps a compatibility `BuildRequestBody(...)` wrapper around the writer-based implementation

So the real remaining work is:

1. remove `BuildRequestBody` from the interface,
2. delete the compatibility wrappers,
3. finish any remaining `GetTextString()` cleanup at downstream boundaries.

### Confirmed partial / still open

- replay/fork orchestration still has some explicit string materialization in host/frontend paths.
- CLI/TUI boundaries still contain `GetTextString()` reads, which is acceptable at display boundaries but not fully cleaned up.

### Solidified verdict

**Plan 0017 core migration is functionally complete.**  
What remains is compatibility-surface removal and frontend/replay cleanup, not fundamental message-pipeline redesign.

## Plan 0018 — Utf8String Type Redesign

### Confirmed completed

- `Utf8String` exists as the canonical immutable UTF-8 text type.
- implemented storage kinds are:
  - `Empty`
  - `ManagedArray`
  - `StaticLiteral`
- internal trusted literal path exists via `FromTrustedUtf8Literal(...)`.
- explicit `ToString()` materialization boundary is present.
- `Utf8String` implements `IUtf8SpanFormattable`.
- JSON converter exists and round-trip tests are present.
- cross-kind structural equality is tested.

### Important correction to the original report

The original report listed `Utf8String.cs` as `266 lines`.

Current verified size is **288 lines**.

### Confirmed still open

- there is **no native/off-heap storage mode implemented yet**.
- `Utf8StringStorageKind.NativeBuffer` from the plan does not exist in the current code.
- no `Utf8BufferOwner`/FFI/native-owner model is present yet.

### Solidified verdict

**Plan 0018 is complete for the managed-array + static-literal transitional phase, but not for the full RFC-aligned native/off-heap end state.**

## Bottom Line

The original report's main conclusion is correct: **the UTF-8 migration is no longer aspirational; it is now the active core architecture.**

But the precise status is:

- **0017/0019 are further along than the report claimed** on provider/event/runtime pipeline completion
- **0020 is less adopted than the report claimed** in production call sites
- **0016 still has real cleanup left** in execution/file-processor/CLI helper hotspots
- **0018 still stops short of native/off-heap storage**

So the solidified May 19 status is:

> Core UTF-8 architecture is in place and operational. Remaining work is mostly compatibility cleanup, hotspot follow-through, and adoption of newly-built infrastructure rather than foundational redesign.
