## Executive Summary

Plan 3.7 moved the code in the right direction:

- `OmicronHost` now has `CreateSessionAsync(SessionConfig, ct)` as the async-first session creation API.
- `CreateSession(SessionConfig)` exists as a sync wrapper.
- The legacy parameter-list overload delegates to `SessionConfig` instead of owning construction logic.
- `SessionResumeRequest` and `SessionForkRequest` records were added.
- Basic model metadata primitives exist: `ModelMetadata`, `IModelMetadataSource`, `IModelMetadataMerger`, `ModelMetadataMerger`, and `StaticModelMetadataSource`.
- 388 tests pass with a clean build.

However, the implementation is not fully complete against the plan. The main gaps are:

1. The new host session creation API lacks direct tests.
2. Most tests still use the legacy parameter-list `CreateSession(...)`, so `SessionConfig` is not yet the dominant pattern outside CLI startup.
3. Model metadata is isolated; it is not integrated into `ModelCatalogService` or any refresh/source pipeline.
4. `models.dev` / provider endpoint source skeletons from the plan were not added.
5. The metadata merger does not make output ordering explicitly deterministic.
6. `StaticModelMetadataSource` hard-codes `SupportsTools: true`, which risks false capability metadata.

## Phase 1: Session Creation API Shape

### What is correct

`OmicronHost` now has:

```csharp
public async ValueTask<AgentSession> CreateSessionAsync(
    SessionConfig config,
    CancellationToken ct = default)
```

and:

```csharp
public AgentSession CreateSession(SessionConfig config)
    => CreateSessionAsync(config).GetAwaiter().GetResult();
```

The legacy overload delegates:

```csharp
public AgentSession CreateSession(
    Model model,
    string? systemPrompt = null,
    string? apiKey = null,
    int? maxTokens = null,
    double? temperature = null,
    int maxIterations = 100)
    => CreateSession(SessionConfig.Create(...));
```

This correctly removes the core construction logic from the parameter-list overload.

CLI startup now constructs `SessionConfig` explicitly before creating the session.

### Finding 1 — Missing direct tests for new primary host API

**Severity:** Medium  
**Files:** `Omicron.Core.Tests/`

The plan explicitly called for tests proving:

- `CreateSessionAsync(SessionConfig)` creates a persisted session record with config values.
- `CreateSession(SessionConfig)` delegates correctly.

Search found no tests directly calling `OmicronHost.CreateSessionAsync(SessionConfig, ct)`.

Existing tests still exercise session creation primarily through the legacy overload.

**Recommendation:** Add an `OmicronHostSessionCreationTests.cs` file with at least:

- `CreateSessionAsync_WithSessionConfig_CreatesSessionRecord`
- `CreateSession_WithSessionConfig_SyncWrapperCreatesSessionRecord`
- optional: verifies `SystemPrompt`, model id/provider/API, and session id match the created session.

### Finding 2 — Legacy `CreateSession(model, ...)` remains common in tests

**Severity:** Medium  
**Files:** multiple tests

Many tests still call:

```csharp
host.CreateSession(model)
host.CreateSession(model, "You are a test.")
```

Examples found in:

- `ExtensionRegistryTests.cs`
- `JsonlSessionStoreTests.cs`
- `PersistenceIntegrationTests.cs`
- `SessionProjectionTests.cs`
- `SessionResumeTests.cs`

The legacy overload exists for compatibility, but leaving most tests on it normalizes the old style and weakens the architectural shift toward `SessionConfig`.

**Recommendation:** Update most host-level tests to use:

```csharp
var config = SessionConfig.Create(model, ...);
var session = host.CreateSession(config);
```

Keep one explicit test for the legacy overload if it is intentionally retained.

### Finding 3 — Public request/config APIs lack null guards

**Severity:** Low  
**Files:** `Omicron.Core/OmicronHost.cs`

`CreateSessionAsync(SessionConfig config)`, `ResumeSessionAsync(SessionResumeRequest request)`, and `ForkSessionAsync(SessionForkRequest request)` assume non-null inputs. Passing `null!` causes `NullReferenceException` rather than `ArgumentNullException`.

**Recommendation:** Add:

```csharp
ArgumentNullException.ThrowIfNull(config);
ArgumentNullException.ThrowIfNull(request);
```

Also consider validating `config.Model` / `request.Model` if external callers may construct invalid records.

## Phase 2: Async API and `ValueTask` Audit

### What is correct

`CreateSessionAsync` uses `ValueTask<AgentSession>`, which is reasonable because stores can be in-memory and complete synchronously.

The sync wrapper is explicit and isolated:

```csharp
CreateSessionAsync(config).GetAwaiter().GetResult();
```

This is acceptable as a convenience wrapper.

### Finding 4 — Async audit decisions are not documented in code/review

**Severity:** Low  
**Files:** Plan/review docs

Plan 3.7 said to audit and document decisions around `Task` vs `ValueTask` across:

- `OmicronHost`
- `ISessionStore`
- `IEventSink`
- `WorkspaceTransaction`
- `WorkspaceTransactionManager`
- `SlashCommandDispatcher`

The implementation made a sensible `ValueTask` change for session creation, but there is no documented audit outcome for the other areas.

**Recommendation:** Add a short section either to the plan or follow-up review explaining current conventions:

- `ISessionStore` stays `ValueTask` because in-memory store is common.
- `IEventSink` async methods stay `ValueTask`.
- `ResumeSessionAsync` / `ForkSessionAsync` remain `Task` because they enumerate async streams and are not expected to synchronously complete.
- CLI dispatch remains sync until FH-0011.

### What is correct

New metadata primitives are clean and useful:

- `StaticModelMetadataSource`

Tests cover:

- null source entries skipped
- static source maps catalog metadata

### Finding 5 — Metadata is not integrated into `ModelCatalogService`

**Severity:** High for Plan 3.7 completion  
**Files:** `Omicron.Core/Models/ModelCatalogService.cs`

The plan explicitly said:

> Extend `ModelCatalogService` so metadata can be layered onto existing `Model` entries.

Currently `ModelMetadata` is only referenced by:

- `ModelMetadata.cs`
- `ModelMetadataSource.cs`
- `StaticModelMetadataSource.cs`
- tests

There is no integration point in `ModelCatalogService`, no metadata source list, no refresh method, and no way for CLI/model selection to consume enriched metadata.

This means the metadata architecture exists as isolated primitives but is not yet connected to the catalog.

**Recommendation:** Add a minimal catalog metadata surface, for example:

```csharp
public IReadOnlyDictionary<(string ModelId, string ProviderName), ModelMetadata> Metadata { get; }

public ValueTask RefreshMetadataAsync(
    IReadOnlyList<IModelMetadataSource> sources,
    CancellationToken ct = default);
```

or create a separate `ModelMetadataCatalog` service wired beside `ModelCatalogService`.

### Finding 6 — Missing `models.dev` and provider endpoint source skeletons

**Severity:** Medium  
**Files:** `Omicron.Core/Models/`

Plan 3.7 called for:

- `ModelsDevMetadataSource` skeleton
- `IProviderModelMetadataSource` abstraction

Search found neither.

This does not need full network implementation yet, but the skeletons are part of the intended architecture because they shape how metadata discovery will expand.

**Recommendation:** Add:

```csharp
public interface IProviderModelMetadataSource : IModelMetadataSource
{
    string ProviderName { get; }
}
```

and a placeholder `ModelsDevMetadataSource` that returns an empty list / fails closed until the endpoint contract is implemented.

### Finding 7 — Merge output order is not explicitly deterministic

**Severity:** Medium  
**Files:** `Omicron.Core/Models/ModelMetadataSource.cs`

`ModelMetadataMerger.Merge` uses a `Dictionary` and returns:

```csharp
return merged.Values.ToList();
```

Current .NET implementations preserve insertion order, but the code does not make ordering explicit. The plan requires deterministic merge behavior.

**Recommendation:** Sort output explicitly:

```csharp
return merged.Values
    .OrderBy(m => m.ProviderName, StringComparer.OrdinalIgnoreCase)
    .ThenBy(m => m.ModelId, StringComparer.OrdinalIgnoreCase)
    .ToList();
```

Add a test verifying stable output order.

### Finding 8 — Static source hard-codes `SupportsTools: true`

**Severity:** Medium  
**Files:** `Omicron.Core/Models/StaticModelMetadataSource.cs`

`StaticModelMetadataSource` currently does:

```csharp
SupportsTools: true, // all bundled models support tools
```

This risks false capability metadata. `Model` does not currently have an explicit `SupportsTools` property. In metadata, unknown should generally be represented as `null`, not optimistic `true`.

**Recommendation:** Use `null` until tool support can be derived from explicit model/provider capability metadata, or add a proper `SupportsTools` field to `Model` / compatibility descriptors.
