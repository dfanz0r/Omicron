## Phase 1b: Transaction Lifecycle Events (FH-0018)

### Files
- `Omicron.Core/Events/OmicronEvent.cs`
- `Omicron.Core/Workspace/WorkspaceTransaction.cs`
- `Omicron.Core/Workspace/WorkspaceTransactionManager.cs`
- `Omicron.Core/OmicronHost.cs`

### Findings

**✅ Correct:** Four well-modeled event types added:
- `TransactionStartedEvent` (lazy — first stage triggers it)
- `TransactionStagedEvent` (per operation)
- `TransactionCommittedEvent` (success)
- `TransactionRolledBackEvent` (failure, explicit rollback, or dispose without commit)

**✅ Correct:** `WorkspaceTransactionManager` accepts optional `IEventSink` and passes it to `WorkspaceTransaction`.

**✅ Correct:** `OmicronHost` wires `Events` into `WorkspaceTransactionManager`.

**🔴 Untested:** `WorkspaceTransactionTests.cs` has **zero tests** verifying that:
- `TransactionStartedEvent` is emitted on first stage
- `TransactionStagedEvent` is emitted per operation
- `TransactionCommittedEvent` is emitted on successful commit
- `TransactionRolledBackEvent` is emitted on rollback/dispose/failure

The existing 39 transaction tests all use the parameterless constructor (`new WorkspaceTransaction(_host)`) which passes `eventSink: null`. No test exercises the event-emitting path.

**🔴 Design Gap:** All transaction events use `SessionId.Empty`:

```csharp
var envelope = new EventEnvelope(EventId.New(), 0, DateTimeOffset.UtcNow, SessionId.Empty);
```

This means:
1. `InMemoryEventSink.GetSessionEvents(sessionId)` will **exclude** transaction events for any session.
2. If `PersistentEventSink` were ever configured with a session filter, transaction events would not be persisted.

`WorkspaceTransaction` does not know its owning session — it is a workspace-level construct. For MVP this is acceptable, but future audit UIs that query "show me all events for session X" will miss transaction activity.

**Action required:**
1. Add tests that construct `WorkspaceTransaction` with an `IEventSink` and verify event emission counts/types.
2. Document the `SessionId.Empty` design decision. Consider adding a `SessionId?` parameter to `WorkspaceTransaction` in a future pass if session-scoped audit becomes required.

## Phase 2: Transaction Reliability — Journaling & Rollback (FH-0019 + FH-0023)

### Files
- `Omicron.Core/Workspace/WorkspaceTransaction.cs`

### Findings

**✅ Correct:** `CommittedOperation` and `CommittedAction` types are clean and internal-scoped.

**✅ Correct:** On commit failure, the catch block iterates `_journal` in reverse and attempts rollback:
- Write → delete
- Move → move back
- Delete → no-op (documented as best-effort)

**✅ Correct:** `_committed` is reset to `false` on failure so callers can inspect and retry.

**✅ Correct:** `TransactionRolledBackEvent` is emitted on both failure-rollback and explicit rollback.

**🔴 Untested:** The rollback path has **zero test coverage**. `WorkspaceTransactionTests.cs` has no test that:
- Injects a failing `HostWorkspaceFileSystem`
- Verifies that earlier operations are reversed
- Verifies that `_committed` becomes `false`
- Verifies that `TransactionRolledBackEvent` is emitted

The plan explicitly required FH-0023 (commit failure recovery test). The implementation is in place but untested.

**⚠️ Limitation:** Delete rollback is a no-op. If a transaction stages a delete, commits it successfully, then a subsequent operation fails, the delete cannot be undone. This is acknowledged in code:

```csharp
case CommittedAction.Delete:
    // Cannot undelete without backup; best-effort
    break;
```

This is acceptable for MVP but means "atomic" is not fully guaranteed for multi-operation transactions containing deletes. The plan acknowledged this as a best-effort approach.

**⚠️ Potential bug in rollback exception handling:**

```csharp
catch (Exception ex)
{
    rollbackEx = ex;
}
```

If multiple rollback operations fail, only the last exception is preserved. The earlier ones are silently lost. Consider using `AggregateException` or at least logging each failure.

**Action required:** Add commit failure tests. Consider `AggregateException` for multi-failure rollback.

## Phase 4b/c: JSONL Concurrency (FH-0001 + FH-0022)

### Files
- `Omicron.Core/Sessions/SessionStore.cs`
- `Omicron.Core.Tests/JsonlConcurrencyTests.cs`

### Findings

**✅ Correct:** `JsonlSessionStore` uses `ConcurrentDictionary<SessionId, SemaphoreSlim>` for per-session locking.

**✅ Correct:** `AppendEventsAsync` acquires the semaphore with `WaitAsync(ct)` and releases in `finally`.

**✅ Correct:** `JsonlConcurrencyTests` creates 10 tasks × 100 events, verifies count and non-null deserialization.

**⚠️ Gap:** The plan stated the stress test should verify:

> "Sequence numbers are strictly monotonic"

The test does **not** verify sequence numbers:

```csharp
// Missing:
// for (int i = 1; i < allEvents.Count; i++)
//     Assert.True(allEvents[i].Sequence > allEvents[i-1].Sequence);
```

However, this is actually **not testable at the store level** because `JsonlSessionStore` does not stamp sequences — it writes whatever envelope the caller provides. The concurrency test appends `SessionStartedEvent` instances created with `EventEnvelope.ForSession(_sessionId)`, which sets `Sequence = 0`. So all events in the file have `Sequence = 0`.

Sequence stamping happens at the `IEventSink` layer (`InMemoryEventSink` or `PersistentEventSink`), not at the store. The test bypasses the sink and writes directly to the store.

**Recommendation:** Either:
1. Update the test to stamp sequences before appending (mimic the sink), then verify monotonicity; or
2. Remove the "sequence monotonicity" claim from the plan's exit criteria for this test.

The current test validates the right thing (concurrent appends don't corrupt the file) but not sequence ordering.

**No action required** — the test is correct for its purpose; just update the plan document if sequence verification is important.
