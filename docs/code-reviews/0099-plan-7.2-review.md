## Executive Summary

The architecture is clean: shared host init, model picker, API key prompt, slash command bridge, and AppLayout integration all wired together in `RunTuiSessionAsync`. However, **two Critical bugs break the entire TUI flow**: `TuiShell` hardcodes Ctrl+D as a global exit that bypasses modal handlers, and `TuiShell.RunAsync` cannot be called twice on the same instance (required by picker → prompt → AppLayout sequence).

---

## Critical Findings

### Finding 1 — CRITICAL: `TuiShell` hardcodes Ctrl+D as global exit, bypassing all modal handlers

**File:** `Omicron.CLI/Tui/TuiShell.cs` (lines ~100–110)  
**Severity:** Critical  
**Category:** Correctness

#### Problem

Inside `RunAsync`, before calling the caller's `onEvent`:

```csharp
if (evt is KeyEvent ke)
{
    if (ke.Key == Key.Character && ke.Text?.Value == 4) // Ctrl+D
        break; // ← exits the loop immediately
}

bool needsRender = await onEvent(evt); // ← never called for Ctrl+D
```

This means:
- **Model picker:** The picker's `HandleKey` checks for Ctrl+D to cancel, but it's never reached. The shell breaks the loop and `await pickerTask.Task` hangs forever (TaskCompletionSource never set).
- **API key prompt:** Same issue — Ctrl+D bypasses the prompt's escape handling.
- **AppLayout:** The AppLayout's Ctrl+D handler (which checks `_input.HasContent`) is bypassed — you can't type Ctrl+D as a character in the input line.

#### Fix

Remove the hardcoded Ctrl+D check from `TuiShell.RunAsync`. Let the caller handle it:

```csharp
// REMOVE this block entirely:
// if (evt is KeyEvent ke)
// {
//     if (ke.Key == Key.Character && ke.Text?.Value == 4)
//         break;
// }
```

The existing callers already handle exit:
- `AppLayout.OnTerminalEvent` checks Ctrl+D + empty input → calls `Exit()` → `_shell.Cancel()`
- Model picker and API key prompt handle Ctrl+D in their own `HandleKey`

**Exception:** If we want a "break glass" emergency exit, keep it but ONLY when no modal is active. Add a `IsModalActive` flag or check if `onEvent` returned false (unhandled).

### Finding 2 — CRITICAL: `TuiShell.RunAsync` cannot be called twice on the same instance

**File:** `Omicron.CLI/Tui/TuiShell.cs`  
**Severity:** Critical  
**Category:** Correctness

#### Problem

`RunTuiSessionAsync` calls `shell.RunAsync` three times on the same `TuiShell` instance:
1. For the model picker
2. For the API key prompt (if needed)
3. For the AppLayout chat loop

`TuiShell` creates `_cts` and `_renderSignal` in the constructor. After the first `RunAsync`:
- The `eventStream` enumerator is disposed in `finally`
- `_cts` is NOT reset (only cancelled by `Cancel()`)
- `_renderSignal` channel may have stale unread items

On the second `RunAsync`, a NEW `eventStream` is created from `_backend.ReadEvents(_cts.Token)`. But if `_cts` was never cancelled, it works. However, the `_renderSignal` channel may have a stale `true` from the previous run, causing an immediate render of the old frame before any events.

More importantly: `TerminalScope.UseAlternateScreen` and `HideCursor` are created inside `RunAsync` with `using`. Each call enters alternate screen again. Three calls = three nested alternate screen scopes. The ref-counting in `TerminalScope` handles this, but it's fragile.

#### Fix

Either:

**Option A:** Make `TuiShell.RunAsync` reset its internal state (new `_cts`, new `_renderSignal`) at the start:

```csharp
public async Task RunAsync(...)
{
    // Reset state for a fresh run
    if (_cts.IsCancellationRequested)
    {
        _cts.Dispose();
        _cts = new CancellationTokenSource();
    }
    // Drain any stale render signals
    while (_renderSignal.Reader.TryRead(out _)) { }
    // ... rest of method
}
```

**Option B:** Use a single `RunAsync` call and implement modals as overlays within the same event loop (more complex but cleaner).

**Option C (MVP):** Create a new `TuiShell` for each phase (picker, prompt, app). Simplest:

```csharp
// Picker phase
using (var pickerShell = new TuiShell(new SystemTerminalBackend()))
{
    pickerShell.Backend.Initialize();
    await pickerShell.RunAsync(...);
}

// App phase  
using (var appShell = new TuiShell(new SystemTerminalBackend()))
{
    appShell.Backend.Initialize();
    await appShell.RunAsync(...);
}
```

But this causes screen flicker (alternate screen exit/re-enter).

**Recommended fix (Option A):** Add `Reset()` method to `TuiShell`:

```csharp
private void ResetState()
{
    _cts.Dispose();
    _cts = new CancellationTokenSource();
    _disposed = false;
    while (_renderSignal.Reader.TryRead(out _)) { }
}
```

Call `ResetState()` at the start of `RunAsync`.

## High Findings

### Finding 3 — HIGH: `AppLayout.Dispose` disposes `_shell`, but shell is owned by caller

**File:** `Omicron.CLI/Tui/AppLayout.cs` (line ~245)  
**Severity:** High  
**Category:** Lifetime Management

#### Problem

```csharp
public void Dispose()
{
    _cts.Cancel();
    _cts.Dispose();
    _shell.Dispose(); // ← AppLayout disposes shell
}
```

But `RunTuiSessionAsync` creates the shell:
```csharp
using var shell = new TuiShell(backend);
// ...
using var app = new AppLayout(shell, session);
await app.RunAsync(); // app.RunAsync completes
// app.Dispose() called by using — disposes shell
// shell.Dispose() called by using — double dispose!
```

`TuiShell.Dispose` has guard `if (_disposed) return;`, so double-dispose is safe. But it's still a code smell — the shell's lifetime should be managed by `RunTuiSessionAsync` only, not by AppLayout.

#### Fix

Remove `_shell.Dispose()` from `AppLayout.Dispose()`. The shell is borrowed, not owned:

```csharp
public void Dispose()
{
    if (_disposed) return;
    _disposed = true;
    _cts.Cancel();
    _cts.Dispose();
    // Do NOT dispose _shell — it's owned by the caller
}
```

### Finding 4 — HIGH: `TuiSlashCommandBridge` delegates `/model` to nowhere

**File:** `Omicron.CLI/Tui/TuiSlashCommandBridge.cs` (line ~55)  
**Severity:** High  
**Category:** Feature Gap

#### Problem

```csharp
default:
    // Delegate to existing console dispatcher for /model, etc.
    return false;
```

`/model` is not actually delegated. It falls through to normal session submission, so the user accidentally sends `/model gpt-4` as a chat message to the LLM.

#### Fix

Either implement `/model` in the bridge or show a "not yet implemented" message:

```csharp
case "/model":
    displayMessage = "/model switching not yet implemented in TUI. Use /exit and restart with --tui.";
    return true;

default:
    displayMessage = $"Unknown command: {command}";
    return true;
```

## Medium Findings

### Finding 5 — MEDIUM: `TuiApiKeyPrompt` cursor uses string length, not display width

**File:** `Omicron.CLI/Tui/TuiApiKeyPrompt.cs` (line ~95)  
**Severity:** Medium  
**Category:** Correctness (i18n)

#### Problem

```csharp
int cursorCol = dialogX + 3 + _input.Length;
```

For API keys this is fine (ASCII-only). But if someone pastes a multi-byte character, the cursor misaligns.

#### Fix

Use display width:

```csharp
int cursorCol = dialogX + 3 + GetDisplayWidth(_input.ToString());
```

(Or just document the limitation since API keys are ASCII.)

### Finding 6 — MEDIUM: Slash command `/help` is shown as `SessionErrorEvent` (red)

**File:** `Omicron.CLI/Tui/AppLayout.cs` (line ~175)  
**Severity:** Medium  
**Category:** UX

#### Problem

```csharp
_transcript.UpdateFromEvent(new SessionErrorEvent(
    EventEnvelope.ForSession(_session.Id), displayMessage, "info"));
```

`SessionErrorEvent` renders with red text (error style). `/help` output should be neutral or green, not red.

#### Fix

Add the message as a `SystemNoticeBlock` instead:

```csharp
_transcript.Store.AppendNotice(displayMessage);
_transcript.Layout.InvalidateFrom(BlockId.None);
_transcript.Layout.ReflowForWidth(...);
_transcript.Viewport.UpdateTotalRows(...);
```

Or create a dedicated `SystemNoticeEvent` that renders with neutral style.
