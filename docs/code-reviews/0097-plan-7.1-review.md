# Code Review 0097: Plan 7.1 — Transcript Viewport and App Layout

**Status:** Review Complete — 3 Critical, 3 High, 3 Medium findings  
**Date:** 2026-05-10  
**Build:** 0 errors, 0 warnings (pre-existing xUnit analyzer warnings only)  
**Tests:** 657 pass (31 new), 0 failures

---

## Executive Summary

The architecture is solid: transcript store with block-level metadata, layout cache with grapheme-aware wrapping, viewport state machine, and a measure/arrange/render widget system. However, **three Critical bugs break core TUI behavior**: streaming text never appears until completion, style lookup is quadratic, and the status bar has the same CJK alignment bug we already fixed once.

## Critical Findings

### Finding 1 — CRITICAL: Assistant streaming text is invisible until response completes

**File:** `Omicron.CLI/Tui/TranscriptViewportWidget.cs` (lines ~85–115, ~155–165)  
**Severity:** Critical  
**Category:** Correctness / UX

#### Problem

`UpdateFromEvent` buffers all `AssistantTextDeltaEvent` deltas:

```csharp
case AssistantTextDeltaEvent delta:
    _pendingAssistantText.Append(delta.Delta);
    _pendingAssistantBytes += Encoding.UTF8.GetByteCount(delta.Delta);
    break; // ← does NOT update store or layout

case AssistantResponseCompleteEvent complete:
    if (_pendingAssistantText.Length > 0)
    {
        var utf8 = Encoding.UTF8.GetBytes(_pendingAssistantText.ToString());
        _store.AppendAssistantDelta(utf8); // ← only flushes here
        _store.CompleteLastAssistantBlock();
        _pendingAssistantText.Clear();
    }
    RebuildLayout();
    break;
```

The user sees **zero assistant text** until the entire response finishes. The TUI is non-interactive during streaming — no partial words, no cursor activity, nothing. This defeats the primary purpose of a TUI over a simple console mode.

#### Fix

Flush pending text on every delta (or every Nth delta / every N ms) and trigger a layout update + render request:

```csharp
case AssistantTextDeltaEvent delta:
    _pendingAssistantText.Append(delta.Delta);
    _pendingAssistantBytes += Encoding.UTF8.GetByteCount(delta.Delta);
    
    // Flush pending text to store so it becomes visible
    if (_pendingAssistantText.Length > 0)
    {
        var utf8 = Encoding.UTF8.GetBytes(_pendingAssistantText.ToString());
        _store.AppendAssistantDelta(utf8);
        _pendingAssistantText.Clear();
        _pendingAssistantBytes = 0;
        
        // Only re-layout the last block (incremental)
        _layout.InvalidateFrom(_store.Blocks[^1].Id);
        _layout.ReflowForWidth(Math.Max(1, _bounds.Width), _store);
        _viewport.UpdateTotalRows(_layout.TotalWrappedRows);
        _shell.RequestRender(); // Need access to shell, or use a render-request callback
    }
    break;
```

**Better architecture:** Pass an `Action requestRender` callback into the widget constructor, or have `AppLayout` poll the transcript widget for dirty state each frame.

**For MVP:** At minimum, flush the pending buffer and append to the store inside the delta handler. The layout can be rebuilt lazily (e.g., only when the pending buffer exceeds 20 characters or 100 ms elapsed).

### Finding 2 — CRITICAL: `GetStyleForBlock` is O(N) per wrapped line = O(N²) per frame

**File:** `Omicron.CLI/Tui/TranscriptViewportWidget.cs` (lines ~205–225)  
**Severity:** Critical  
**Category:** Performance

#### Problem

```csharp
private TextStyle GetStyleForBlock(BlockId blockId)
{
    foreach (var block in _store.Blocks) // ← O(N) where N = block count
    {
        if (block.Id == blockId)
        {
            return block switch { ... };
        }
    }
    return defaultStyle;
}
```

Called once per visible wrapped line. For a conversation with 100 blocks and a viewport showing 50 lines: 5,000 block comparisons per frame. At 60 FPS with streaming: **300,000 comparisons/second**.

#### Fix

Build a `Dictionary<BlockId, TranscriptBlock>` in `RebuildLayout` (or maintain it incrementally):

```csharp
private readonly Dictionary<BlockId, TranscriptBlock> _blockById = new();

private void RebuildLayout()
{
    _blockById.Clear();
    foreach (var block in _store.Blocks)
        _blockById[block.Id] = block;
    // ... rest of rebuild
}

private TextStyle GetStyleForBlock(BlockId blockId)
{
    if (_blockById.TryGetValue(blockId, out var block))
    {
        return block switch { ... };
    }
    return TextStyle.Default;
}
```

O(1) per line. Total: 50 lookups/frame.

### Finding 3 — CRITICAL: `StatusBarWidget` uses `string.Length` for alignment

**File:** `Omicron.CLI/Tui/StatusBarWidget.cs` (lines ~55–70)  
**Severity:** Critical  
**Category:** Correctness (i18n)

#### Problem

Same bug we fixed in `SimpleStatusBar` (Review 0095 Finding 15):

```csharp
int centerCol = _bounds.X + (_bounds.Width - ProviderName.Length) / 2;
int rightCol = _bounds.Right - StatusText.Length - 1;
```

CJK text is misaligned. `"日本語"` has `Length == 3` but display width 6.

#### Fix

Add `GetDisplayWidth` helper (same as `SimpleStatusBar`):

```csharp
private static int GetDisplayWidth(string text)
{
    int width = 0;
    foreach (Rune rune in text.EnumerateRunes())
        width += CellWidthCalculator.GetWidth(rune);
    return width;
}
```

Use it for center and right column calculations.

## High Findings

### Finding 4 — HIGH: `ViewportState` doesn't account for viewport height when following tail

**File:** `Omicron.Core/Rendering/Transcript/ViewportState.cs` (lines ~35–45, ~75–80)  
**Severity:** High  
**Category:** Correctness

#### Problem

```csharp
public void OnContentAppended(int newTotalWrappedRows)
{
    if (FollowTail)
    {
        _firstVisibleWrappedRow = Math.Max(0, newTotalWrappedRows - 1);
        //                                              ↑ shows only 1 row
    }
}

public void ScrollToBottom(int totalWrappedRows)
{
    _firstVisibleWrappedRow = Math.Max(0, totalWrappedRows - 1);
    //                                      ↑ same issue
}
```

If the viewport is 23 rows tall and the transcript has 100 wrapped rows, following tail should show rows 77–99 (23 rows). Instead it shows row 99 only (1 row).

#### Fix

`ViewportState` needs to know the viewport height. Add it as a field or pass it to methods:

```csharp
public void ScrollToBottom(int totalWrappedRows, int viewportHeight)
{
    _firstVisibleWrappedRow = Math.Max(0, totalWrappedRows - viewportHeight);
    FollowTail = true;
    UnseenLineCount = 0;
}

public void OnContentAppended(int newTotalWrappedRows, int viewportHeight)
{
    int added = newTotalWrappedRows - _lastTotalWrappedRows;
    _lastTotalWrappedRows = newTotalWrappedRows;

    if (FollowTail)
    {
        _firstVisibleWrappedRow = Math.Max(0, newTotalWrappedRows - viewportHeight);
    }
    else
    {
        UnseenLineCount += Math.Max(0, added);
    }
}
```

### Finding 5 — HIGH: `RebuildLayout` does full reflow on every event

**File:** `Omicron.CLI/Tui/TranscriptViewportWidget.cs` (line ~170)  
**Severity:** High  
**Category:** Performance

#### Problem

```csharp
private void RebuildLayout()
{
    _layout.InvalidateFrom(BlockId.None);
    _layout.ReflowForWidth(Math.Max(1, _bounds.Width), _store);
    _viewport.UpdateTotalRows(_layout.TotalWrappedRows);
}
```

Every `UserMessageEvent`, `ToolInvocationStartedEvent`, `ToolInvocationCompletedEvent`, and `SessionErrorEvent` triggers a full reflow of the entire transcript. For a long conversation with 500 wrapped rows, this is 500 re-wraps per streaming session.

#### Fix

Only reflow from the changed block onward. The `InvalidateFrom` method already exists and is designed for this:

```csharp
private void RebuildLayoutFrom(BlockId blockId)
{
    _layout.InvalidateFrom(blockId);
    // Re-layout only invalidated blocks
    // For MVP, ReflowForWidth is acceptable if we only call it for the last block
    // A proper incremental reflow would re-wrap from blockId onwards
    _layout.ReflowForWidth(Math.Max(1, _bounds.Width), _store);
    _viewport.UpdateTotalRows(_layout.TotalWrappedRows);
}
```

**Proper incremental reflow:** `TranscriptLayoutCache` should track which blocks are dirty and only re-wrap those + rebuild the flat list. For MVP, the simplest fix is to only call `RebuildLayout` on discrete events (user message, tool call, completion) and NOT on every delta. Deltas should append to the existing last block and only invalidate that block's lines.

### Finding 6 — HIGH: `InputEditorWidget` cursor position uses `string.Length` not display width

**File:** `Omicron.CLI/Tui/InputEditorWidget.cs` (lines ~155–175)  
**Severity:** High  
**Category:** Correctness (i18n)

#### Problem

```csharp
int cursorScreenCol = x + _cursorPosition; // ← _cursorPosition is string index
```

For `"日本語"` at cursor position 1, `cursorScreenCol = x + 1`, but the first character has width 2. The cursor draws on top of the second half of the first CJK character.

#### Fix

Track cursor display width separately:

```csharp
private int GetCursorDisplayCol()
{
    int col = 0;
    for (int i = 0; i < _cursorPosition; i++)
    {
        if (Rune.DecodeFromUtf8(
            Encoding.UTF8.GetBytes(_buffer[i..]), out var rune, out int consumed) == OperationStatus.Done)
        {
            col += CellWidthCalculator.GetWidth(rune);
        }
    }
    return col;
}
```

Or simpler: compute display width of the substring before cursor.

## Medium Findings

### Finding 7 — MEDIUM: `TranscriptViewportWidget.Render` assumes widget is at Y=0

**File:** `Omicron.CLI/Tui/TranscriptViewportWidget.cs` (line ~195)  
**Severity:** Medium  
**Category:** Correctness

#### Problem

```csharp
context.DrawText(0, row, bytes.Span, style);
```

`row` starts at 0. `RenderContext.DrawText` computes `actualRow = Clip.Y + (y - Clip.Y) = y`. So text is drawn at frame row 0 regardless of where the widget is arranged. Currently works because the transcript is the first child (Y=0), but breaks if layout changes.

#### Fix

```csharp
context.DrawText(_bounds.X, _bounds.Y + row, bytes.Span, style);
```

Same fix needed for the unseen-line indicator:
```csharp
context.DrawText(indicatorX, _bounds.Y + row - 1, ...);
```

### Finding 8 — MEDIUM: `AppLayout.OnRender` doesn't create per-widget clip contexts

**File:** `Omicron.CLI/Tui/AppLayout.cs` (lines ~115–125)  
**Severity:** Medium  
**Category:** Correctness

#### Problem

```csharp
var context = new RenderContext(frame,
    new Rect(0, 0, frame.Width, frame.Height),
    TextStyle.Default);
_root.Render(context);
```

All widgets share the same full-frame clip. A widget that draws outside its arranged bounds is not clipped. The `VStack.Render` should create sub-contexts:

```csharp
public void Render(RenderContext context)
{
    foreach (var child in _children)
    {
        // Get child's bounds (stored during Arrange)
        // Create a clipped sub-context
        var childContext = new RenderContext(
            context.Frame,
            context.Clip.Intersect(childBounds),
            context.DefaultStyle);
        child.Render(childContext);
    }
}
```

This requires storing child bounds in `VStack` (or having children expose their bounds).

#### Fix for MVP

Add a `Bounds` property to `ITuiWidget` (or make it internal). In `VStack.Arrange`, store each child's bounds. In `VStack.Render`, create sub-contexts. Same for `HStack`.

### Finding 9 — MEDIUM: `TranscriptStore` doesn't clear `_lastAssistantBlockId` on non-assistant appends

**File:** `Omicron.Core/Rendering/Transcript/TranscriptStore.cs` (lines ~40, ~95, ~125)  
**Severity:** Medium  
**Category:** Correctness

#### Problem

```csharp
public UserMessageBlock AppendUserMessage(...)
{
    ...
    _lastAssistantCompleted = true; // ← marks complete
    // but _lastAssistantBlockId is NOT cleared
    return block;
}
```

After a user message, `_lastAssistantBlockId` still points to the old assistant. If `AppendAssistantDelta` is called, it checks `_lastAssistantCompleted` (true) and creates a new block, which is correct. But `_lastAssistantBlockId` is stale. Not a bug today, but confusing and fragile.

#### Fix

```csharp
public UserMessageBlock AppendUserMessage(...)
{
    ...
    _lastAssistantBlockId = null;
    _lastAssistantCompleted = true;
    return block;
}
```

Same for `AppendToolCall` and `AppendNotice`.

## Observations (Non-blocking)

### Observation A — `TranscriptLayoutCache.InvalidateBlock` uses `List.Remove` in a loop

`List<T>.Remove` is O(N) with a linear search. For a block with 100 wrapped lines, removing them one by one is O(10,000). For MVP with typical conversation sizes, this is fine. Future optimization: rebuild the flat list from scratch when invalidating.

### Observation B — `WrappedLineInfo.CellStart` is always 0

In `WrapLogicalLine`, `CellStart` is always passed as 0. For continuation rows, it should probably be the starting cell offset (always 0 since rows start at col 0). This is correct for the current wrapping strategy but the field is redundant.

### Observation C — `AppLayout.OnTerminalEvent` is async but doesn't await input handling

```csharp
private async Task<bool> OnTerminalEvent(TerminalEvent evt)
{
    switch (evt)
    {
        case KeyEvent ke:
            if (_input.HandleKey(ke)) // ← synchronous
                return true;
            ...
    }
    return false;
}
```

The method is `async` but never `await`s. This is fine (the compiler generates a state machine unnecessarily), but it could be `bool` instead of `Task<bool>` if the signature allows. The `TuiShell.RunAsync` signature requires `Func<TerminalEvent, Task<bool>>`, so this is unavoidable.

### Observation D — `RenderContext.DrawText` clipping for X-axis is incomplete

```csharp
if (x >= Clip.Right)
    return;
int maxWidth = Clip.Right - x;
```

It clips `x >= Clip.Right` but doesn't clip `x < Clip.X`. If a widget draws at x=-5, it passes the check and writes to the frame. The `Frame.SetText` method handles negative row/col by returning early, so this is harmless but inconsistent.

## Verdict

**Do not proceed to Plan 8 until P0 and P1 findings are resolved.**

Finding 1 (streaming invisible) is a showstopper — the TUI provides no value over console mode if streaming text doesn't appear. Findings 2 and 3 are small fixes with high impact. Finding 4 (viewport height) makes the scroll behavior unusable for any viewport taller than 1 row.

The architecture (store → layout cache → viewport state → widget tree) is well-designed and will serve downstream plans well once these correctness issues are fixed.
